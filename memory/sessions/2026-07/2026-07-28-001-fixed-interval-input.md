## 摘要

确认并实现固定间隔从单一分钟框动态拆分为分钟、小时和天的输入方式，完成整组提交、空分量按 0、自动进位、365 天上限和非法输入持久化隔离。随后对用户报告的 1 GB 内存进行不附加 Visual Studio 的 Debug、Release、纯净 WPF 和软件渲染对照测量，确认异常主要来自本机 WPF 硬件渲染路径，并说明硬件与软件渲染不会改变 WPF 框架本身。

## 关键要点

- 不足 60 分钟只显示分钟；达到 60 分钟显示小时和分钟；达到 24 小时显示天、小时和分钟；最大 365 天，不显示年。
- 天、小时和分钟允许自动进位，合法结果统一换算为总分钟后规范化显示。
- 子输入框之间移动焦点不提交；按 Enter 或离开整个表单区域才统一提交。
- 单个空分量按 0 参与整组换算；例如从 10 小时 38 分钟清空小时后，结果规范化为 38 分钟。全部分量为空或合计为 0 时才因低于最小间隔而拒绝应用。
- 非数字、合计为 0、超过 365 天和异常长输入不修改事件。
- UI 非法草稿不进入 Logic；持久化只导出 Logic 的有效状态，因此其他即时保存和低频保存仍保留最后一次合法值。
- 独立 Debug 和 Release 的硬件渲染可见工作集都约 1.1 GB，纯净空白 .NET 10 WPF 窗口也约 1.04 GB；完整 Reminder 软件渲染可见约 180–184 MB、隐藏约 19–25 MB，托管堆约 7 MB。
- 本次没有改变正式默认渲染方式。软件渲染降低本机内存，但可能提高 CPU 并影响动画，需要以后结合更多设备测量决定。
- Reminder 当前仍是 WPF；正常启动采用 WPF 默认的硬件优先路径，已有 `REMINDER_SOFTWARE_RENDERING=1` 诊断开关可以在不重写 UI 的情况下强制同一套 WPF 使用软件渲染。
- QQ、微信等应用的任务管理器内存不能直接证明其使用软件渲染；进程划分、共享工作集、GPU 进程、缓存和按需加载都会影响显示值。
