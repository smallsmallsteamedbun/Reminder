## 1. 项目概述

Reminder 是一个运行在 Windows 系统上的桌面提醒程序。程序主要用于：

- 定时提醒用户休息眼睛。
- 定时提醒用户喝水。
- 提醒用户创建的其他自定义事件。

程序预计长期在后台运行，通过简洁、符合 Windows 使用习惯的方式提供提醒，不持续占用桌面空间。

## 2. 项目目标

1. 帮助长时间使用电脑的用户建立规律的休息和饮水习惯。
2. 为喝水、休息眼睛和自定义事件提供相互独立、可配置的提醒能力。
3. 尽可能保持较低的内存和 CPU 占用，避免明显影响电脑性能。
4. 使用自然、克制、符合 Windows 使用习惯的提醒和交互方式。
5. 保持界面简洁明了，使用户无需新手引导也能理解和使用主要功能。
6. 确保程序在长期后台运行时保持稳定。

## 3. 功能需求

### 3.1 提醒事件

- 所有提醒事件使用相同的事件模型，不区分不可删除的内置事件与普通事件，也不存在功能上特殊的事件类型。
- 程序首次使用时提供“喝水”和“休息眼睛”两个示例事件。
- 两个示例事件默认均不启用；用户开启它们即可开始使用最基础的喝水和休息提醒功能。
- 示例事件可以删除。
- 用户可以添加、设置和删除其他自定义提醒事件。
- 用户点击“添加事件”后，事件列表中立即出现一条使用默认属性的新事件，用户可以直接在该事件中继续填写和修改。
- 新事件不在事件列表当前可见范围内时，列表应自动纵向滚动到能够看到该事件的位置，并短暂高亮新事件的卡片边框。
- 事件列表支持使用鼠标滚轮上下滚动；即使鼠标位于单条事件内部的横向滚动区域上，也应优先保证列表的纵向滚轮操作有效。
- 单条事件内部存在横向可滚动内容时，应支持触摸板横向手势等系统横向滚动输入；鼠标配合横向滚动手势时也不应只能依赖拖动滚动条。
- 下拉菜单、事件列表和事件卡片等所有存在可滚动范围的区域，都应将相应滚轮或触摸板输入交给当前可滚动区域，避免只能拖动滚动条。下拉菜单收起时，鼠标滚轮不得直接更改当前选项；下拉菜单展开后，鼠标位于弹出选项列表内时，滚轮只滚动该列表；鼠标转到主页滚动时，先收起当前展开的下拉菜单，再正常滚动主页。
- 鼠标滚轮滚动应采用类似 Windows 设置页面的平滑滚动动画，具有自然的启动和减速过程，不直接跳变滚动位置。
- 新事件的自动定位也应平滑滑动到目标位置；到达后再突出显示新事件，避免直接跳转造成生硬感。
- 事件列表后续需要提供事件搜索输入框；具体搜索范围、匹配规则和结果交互尚待讨论，`0.2.0` 暂不实现。
- 每条事件具有一个不向用户展示的内部 `event id`；程序使用该字段识别事件唯一性，不使用事件名称作为唯一标识。
- 不同事件允许使用相同名称。
- 事件名称默认是“新建事件”，在事件列表第一列使用文本框显示；用户可以直接点击文本框修改。
- 事件名称最多允许 50 个加权字符：ASCII 字符按 1 个计算，中文等非 ASCII 字符按 2 个计算，因此最多可输入 25 个中文字符或 50 个英文字符；混合输入按相同权重累计。
- 事件名称文本框不需要无意义占满卡片，但在默认窗口和默认缩放下应能够完整显示达到最大允许长度的常见中文、英文或混合名称。
- 新建自定义事件默认不暂停，暂停/恢复按钮默认显示“暂停”。
- 新建自定义事件默认开启。
- 新建自定义事件默认采用固定时间事件，固定提醒间隔默认为 45 分钟。
- 每个事件分别独立计时，互不共用计时状态。
- 用户可以单独启用或禁用每个事件。
- 事件卡片第一行靠后显示该事件的开启或关闭滑块，删除操作位于其后。
- 事件卡片的“删除”按钮使用红色填充和红色边框，清楚表达危险操作。
- 点击删除后不得立即删除事件；程序应弹出确认框询问“是否删除事件”，提供“确定”和“取消”两个按钮。只有点击“确定”才删除，确认按钮使用红色填充和红色边框。
- 确认删除事件后，原来位于该事件下方的事件卡片应通过平滑上移动画依次填补空位，不应直接跳到新位置。
- 用户将事件从开启切换为关闭时，界面开关滑向关闭，并停止该事件当前调度；固定时间事件同时保留暂停状态和剩余时间。
- 固定时间事件同时处于关闭和暂停时，用户直接切换为开启只改变开关状态，仍保持暂停；用户随后可以通过“恢复”按钮继续计时。
- 指定时间事件不显示单项暂停按钮，其单项暂停与关闭使用同一套界面和调度语义；直接切换为开启时恢复其日历调度。
- 用户成功修改一个事件的名称、时间、类型、频率、终止次数或其他设置后，该事件自动切换为开启并取消单项暂停，立即按照修改后的设置继续运行。
- 用户事件界面应同步显示每个提醒事件的倒计时。
- 倒计时为只读数据，精确到秒：
  - 大于或等于 1 天时采用“天、时、分、秒”显示；
  - 大于或等于 1 小时且小于 1 天时采用“时、分、秒”显示；
  - 小于 1 小时时只显示“分、秒”；
  - 天数不设显示上限。
- 对已经失效、未来不会再发生的事件，通常不显示倒计时；每次程序启动时有 5% 概率在倒计时位置显示彩蛋文字“弹一万遍反方向的钟”，并在本次启动期间保持该结果。
- 程序不设置或显示事件的已完成次数。

### 3.2 提醒时间设置

- 每个事件独立选择并配置以下两种提醒时间模式之一：
  1. 固定时间间隔：从保存该设置时开始计时，之后按照用户设置的固定时间间隔提醒。
  2. 指定时间与频率：设置一个指定时间进行提醒，并选择提醒频率为“一次性”“每天”“每周”“每月”或“每年”。
- 事件类型使用左右两个等宽选项组成的分段选择器，不使用普通开关外观；“固定时间事件”和“指定时间事件”分别显示在左右区域，当前选中区域显示底色。
- 固定时间间隔模式允许每个事件单独设置提醒间隔。
- 固定时间间隔在内部统一换算为总分钟数，合法范围为 1 分钟至 365 天（525600 分钟）；新建自定义事件默认 45 分钟。
- 固定时间间隔表单按照当前合法总时长动态显示：
  - 小于 60 分钟时，只显示“分钟”输入框；
  - 大于或等于 60 分钟且小于 24 小时时，显示“小时、分钟”输入框；
  - 大于或等于 24 小时时，显示“天、小时、分钟”输入框；
  - 最大间隔为 365 天，不提供“年”输入框。
- 天、小时和分钟允许通过超出常规分量范围的非负整数自动进位；用户确认后，程序统一换算为总分钟并重新按规范分量展示。例如 90 分钟规范化为 1 小时 30 分钟。
- 任一固定间隔分量输入框留空时按 0 参与整组换算；只要其余分量合计仍处于合法范围，整组输入有效并在确认后收起不再需要的输入框。例如从“10 小时 38 分钟”删除小时值后，结果规范化为“38 分钟”。全部分量留空或合计为 0 仍然非法。
- 用户在拆分输入框之间移动焦点时，不立即换算或重排；只有在任一固定间隔输入框按下 Enter，或者焦点离开整个固定间隔表单区域时，才统一校验、换算和重排。
- 指定时间与频率模式允许每个事件单独设置提醒时间和提醒频率。
- 新建事件切换为指定时间事件后，频率默认选择“仅一次”。
- 指定时间与频率模式的输入项和摘要显示随频率变化：
  - 一次性：设置日期和具体时间；
  - 每天：设置具体时间，摘要显示“每天 + 时间”；
  - 每周：设置星期几和具体时间，摘要显示“星期 + 时间”；
  - 每月：设置每月几日和具体时间，摘要显示“每月日期 + 时间”；
  - 每年：设置月份、日期和具体时间，摘要显示“每年月份、日期 + 时间”。
- 指定时间表单按“年、月、日、时、分”拆成独立数值输入框并在输入框后显示单位，不要求用户在一个文本框中输入完整日期时间：
  - 仅一次：年、月、日、时、分；
  - 每天：时、分；
  - 每周：星期下拉菜单、时、分；
  - 每月：日、时、分；
  - 每年：月、日、时、分。
- 日期和时间各部分必须分别校验范围，并在组合后再次校验日期是否真实存在；小时允许 `0–23`，分钟允许 `0–59`，分钟输入 `0` 和 `00` 都是合法输入。
- 用户切换或选择某个指定时间频率时，该频率所需的日期、星期和时间字段默认以选择时刻的一小时之后初始化。
- 除频率为“仅一次”的指定时间事件外，事件使用“终止次数”控制自动结束，不再提供截止时间设置：
  - 使用下拉菜单；
  - 选项为“不终止”以及 1 次至 100 次；
  - 默认选择“不终止”；
  - 选择有限次数时显示剩余次数；
  - 普通提醒最终被完成或跳过本次后扣减 1 次；
  - 点击延迟时不扣减，延迟后再次出现仍属于同一次提醒，最终完成或跳过时只扣减 1 次；
  - 点击通知关闭叉号属于“跳过本次”，按跳过规则扣减 1 次；
  - 通知自行消失属于“延迟”，按延迟规则处理，不在自动消失时扣减；
  - 恢复时发送的纯信息“已跳过”汇总也要扣减终止次数；汇总中列出的每个不同事件分别扣减 1 次，同一事件在同一段不可提醒状态中即使错过多次也只汇总并扣减 1 次；
  - 剩余次数减到 0 后自动关闭事件，并将下拉菜单显示为“不终止”。
- 指定时间事件选择“仅一次”时，不显示终止次数设置；该事件完成或错过这次唯一计划后，按照一次性事件规则关闭。
- 指定时间与频率模式不要求用户设置的时间必须晚于当前时间，也不因时间位于过去而拒绝保存。
- 对循环提醒，程序按照循环规则寻找未来仍可发生的提醒时间。
- “每月”或“每年”循环遇到本周期不存在的日期时，直接跳过该周期，不改成该周期的最后一天。例如每月 29 日提醒在平年 2 月不提醒，1 月 29 日之后的下一次为 3 月 29 日。
- 对一次性提醒，如果指定时间已经过去，则按错过提醒处理：提示一次“已跳过”，不再安排下一次提醒，事件保留在列表中并自动切换为关闭。
- 对上述已经结束且自动关闭的事件，程序使用计划时间和事件开关状态判断是否需要处理，不为单次计划额外保存“是否已经处理”的标记；事件关闭后不再重复提示同一个过去计划。

### 3.3 暂停、恢复、重启与本次延迟

- 用户可以通过暂停/恢复按钮单独暂停固定时间间隔事件；指定时间与频率事件不显示单项暂停按钮，使用开启/关闭开关停止或恢复该事件。
- 用户可以暂停全部事件的计时：
  - 当前正在计时的事件进入暂停状态。
  - 尚未开始计时的事件如果在全局暂停期间到达预定开始时刻，也不发送提醒。
  - 结束暂停后，各事件按照自身设置的固定间隔或指定时间与频率恢复正常调度。
- 开启全部暂停后，暂停时长下拉设置出现在“全部暂停/全部恢复”按钮左侧的同一操作行；该区域预留位置，不得因设置出现而推动全局按钮移动。
- 全部暂停时长提供以下选项：
  - 直到手动恢复；
  - 1 分钟；
  - 5 分钟；
  - 10 分钟；
  - 15 分钟；
  - 30 分钟；
  - 1 小时；
  - 2 小时；
  - 5 小时。
- 全部暂停默认选择“直到手动恢复”；在该选项下，除非用户手动恢复，否则程序不会自动恢复提醒。
- 选择具体暂停时长时，下拉设置后方显示暂停剩余时间倒计时。
- 选择“直到手动恢复”时，不显示暂停剩余时间倒计时。
- 固定时间间隔事件处于暂停状态时，其计时冻结，不在暂停期间产生新的到点提醒。
- 单项暂停或全部暂停结束后，固定时间间隔事件从暂停前保存的剩余时间继续计时，不重新开始一个完整间隔。
- 采用指定时间与频率模式的事件，如果提醒时间落在暂停期间，则当提醒恢复时提示一次该提醒“已跳过”，随后按照原有时间规则继续调度。
- 程序应提供恢复提醒的操作。
- 主页面把“全部暂停”和“全部恢复”合并为同一个切换按钮：未处于全部暂停时显示“全部暂停”，进入全部暂停后显示“全部恢复”。
- “全部暂停”暂停所有已开启事件的倒计时；“全部恢复”恢复所有已开启事件的倒计时。对已开启的固定时间事件，“全部恢复”同时解除原有的单项暂停，不保留其手动暂停状态。
- 用户可以重启某一个事件的提醒，也可以重启全部事件的提醒。
- “全部暂停”对所有事件类型生效。
- “全部重启”只检查事件是否开启：所有已开启的固定时间间隔事件都从新的完整间隔重新开始，同时解除这些事件原有的单项暂停；指定时间与频率事件不受影响。
- 单项“重启”仍只适用于当前已经开始计时、且采用固定时间间隔的事件。
- 指定时间与频率事件不能重启，事件卡片中不显示“重启”按钮。
- 指定时间与频率事件不显示单项暂停/恢复按钮；开启与关闭承担该事件的单项停止和恢复操作。
- 指定时间事件处于关闭状态且仍存在未来计划时，倒计时标题显示“距离下次发生但不提醒”，仍显示下一次计划发生的只读倒计时。
- 重启单个事件或重启全部事件时，符合重启条件的固定时间间隔事件都清除本轮已经经过的时间，从 `0` 开始一轮新的完整间隔。
- 提醒到达时，用户可以在通知中直接选择“完成”“延迟”或“跳过本次”。
- 用户点击“完成”后，该事件从实际完成时间开始重新计算下一轮时间。
- 用户选择延迟时，程序直接将当前提醒的剩余时间设为所选延迟时长；倒计时结束后再次提醒，不另设独立的延迟状态或延迟剩余字段。
- 延迟时长默认为 5 分钟；用户可以在设置中修改统一的延迟时长，但不能为不同事件分别设置不同的延迟时长。
- 对固定时间间隔事件，本次实际延迟时长取“全局延迟时长”和“该事件固定提醒间隔”中的较小值；固定提醒间隔短于全局延迟时长时，使用固定提醒间隔进行延迟。
- 延迟本次提醒的操作可能导致全屏游戏退出全屏。程序无需尝试规避该系统表现，但应向用户说明这是正常现象；需要避免退出全屏时，用户可将游戏设置为窗口化。

### 3.4 后台运行与退出

- 程序应能够长期在后台运行，并按照设置的时间触发提醒。
- 程序不应持续显示占用桌面的主窗口。
- 用户关闭可见窗口后，程序应继续在后台运行。
- 程序需要提供系统托盘图标。
- 只有通过系统托盘图标的右键菜单执行“退出”，才退出整个程序。
- 系统托盘右键菜单提供以下项目：
  - 打开主页；
  - 快捷全部暂停；
  - 全部恢复；
  - 显示当前版本号；
  - 退出。
- 托盘中的“快捷全部暂停”始终采用“直到手动恢复”，不会自动选择限时暂停。
- 用户通过系统托盘菜单主动退出程序时，程序应保存当前所有需要恢复的配置与运行状态。
- 软件未运行期间，固定时间间隔事件的计时状态冻结，离线时间不计入间隔；事件原本已经暂停时，其暂停属性和计时状态一并保存。
- 程序下次启动时应优先读取已有事件及其保存的时间和状态，再恢复调度；固定时间间隔事件从退出时保存的剩余计时继续。
- 如果退出时仍有带“完成”“延迟”“跳过本次”操作、且用户尚未处理的普通提醒，则该次提醒按“已跳过”处理，并在下次满足恢复条件时纳入错过提醒提示。
- 当前剩余时间因“延迟”操作被改为所选延迟时长后，仍按事件的普通剩余倒计时保存；软件未运行期间该倒计时冻结，下次启动后从保存的剩余时间继续。
- 如果退出时存在限时全部暂停，暂停剩余时间在软件未运行期间同样冻结，下次启动后从保存的剩余时间继续。
- 采用指定时间与频率模式的事件，如果提醒时间落在软件未运行期间，则记录为已跳过，并在下次满足恢复条件时提示；随后按照事件原有规则继续调度。
- 除主动退出时保存完整状态外，程序运行期间约每 1 小时进行一次低频状态保存；该周期无需追求精确，优先减少磁盘活动和资源占用。
- 新建事件、删除事件，或者成功更改事件名称、事件类型、计划参数、终止次数、开关和其他事件设置后，应立即触发一次后台保存，不阻塞界面操作。
- 用户点击“全部暂停”“全部恢复”或“全部重启”并完成对应状态操作后，也应立即触发一次后台保存。
- 用户在全部暂停期间设置或更改限时暂停倒计时后，也应立即保存当时的暂停时长、暂停剩余时间和各事件状态。
- 短时间内连续发生的事件配置保存请求可以合并，但必须保存连续操作后的最新完整状态。
- 全部暂停倒计时设置完成后的时间流逝不要求逐秒写盘；如果程序被强制结束，可以恢复到最近一次即时保存或低频保存时的暂停剩余时间。
- 其他单纯的倒计时流逝，以及单项暂停、单项恢复、单项重启、完成、延迟或跳过等运行状态操作，不要求每次立即写入磁盘；异常退出时允许这些状态回退到最近一次即时保存或低频保存结果，并接受由此造成的小幅提醒节奏变化。
- 用户应能够暂停、恢复和退出程序；具体操作入口将在后续讨论中继续完善。

### 3.5 启动方式

- 程序支持开机自动启动。
- 用户可以自行设置是否启用开机自动启动。
- 程序支持静默启动。
- “静默启动”设置旁应提供一个小问号图标；鼠标移到图标上时显示说明：“程序启动时以后台模式运行，不显示程序面板”。

### 3.6 系统状态变化

- 程序需要处理电脑睡眠、休眠、唤醒、息屏、亮屏、锁屏和解锁对提醒的影响。
- 实际睡眠或休眠不提供用户可配置的计时或通知策略，也不尝试在睡眠或休眠期间发送提醒。
- 因此，实际睡眠或休眠行为不作为单条事件表单中的可选属性；界面如需呈现，只能说明其固定行为。
- 电脑从实际睡眠或休眠唤醒后，对睡眠或休眠期间已经到点的事件提示一次“已跳过”，随后按照各事件原有规则继续调度。
- 息屏和锁屏合并使用同一套事件策略，不分别配置。
- 固定时间间隔事件为“息屏或锁屏”共同配置“继续计时”“重新计时”或“暂停计时”策略。
- 新建固定时间事件的息屏和锁屏策略默认采用“暂停计时”。
- “继续计时”策略允许用户进一步设置在息屏或锁屏期间是否发送普通提醒：
  - 选择发送提醒时，事件在该期间到点后按正常提醒处理。
  - 选择不发送提醒时，事件继续计时；如果在该期间到点，则在之后满足恢复条件时记入一次“已跳过”提示。
- 当用户选择在息屏或锁屏期间发送普通提醒，而显示器已因空闲关闭时，程序应在发送该通知前发出一次短时显示请求，使锁屏画面重新亮起以展示提醒；该操作不得自动解锁电脑，也不得把实际睡眠或休眠改成可提醒状态。
- 选择“继续计时”后显示的是否提醒附加选项，默认选择“不提醒”。
- “重新计时”策略在恢复后从新的完整间隔开始计时。
- “暂停计时”策略在对应系统状态期间冻结剩余时间，并在恢复后继续剩余计时。
- 固定时间间隔事件采用“继续计时”策略时，如果息屏或锁屏期间发生的提醒被抑制，恢复后提示“已跳过”但保持原有固定间隔节奏，不从恢复时刻重新起算。
- 指定时间与频率事件为“息屏或锁屏”共同配置以下方式：
  - “提醒”：事件到点时发送普通提醒；
  - “不提醒”：对应期间不发送普通提醒，之后满足恢复条件时提示一次“已跳过”，再按照原有循环规则继续调度。
- 新建指定时间事件默认选择“不提醒”。
- 错过提醒只有在同时满足以下条件时才进入真正恢复并发送提示：
  - 程序正在运行；
  - 用户已经解锁；
  - 对应事件没有处于单项暂停；
  - 全部暂停已经结束。
- 同一个事件在同一段不可提醒状态中错过多次，只记入一次“已跳过”，不计算或显示具体错过次数。
- 多个不同事件存在已跳过提醒时，在恢复后合并成一条通知，并在通知中列出已跳过的事件。
- 普通提醒已经发出但用户尚未处理时，如果随后进入锁屏或者实际睡眠、休眠状态，则把该普通提醒按“延迟”处理，采用该事件本次应使用的延迟时长重新计时。

### 3.7 通知方式

- 提醒应优先使用 Windows 自带的系统通知机制。
- 通知方式应符合 Windows 的使用习惯，不显得突兀。
- 应尽量使用 Windows 通知中心。
- 应尽量避免自行实现会遮挡屏幕的提醒弹窗。
- 通知本身应提供“完成”“延迟”和“跳过本次”操作，使用户无需先打开程序面板即可处理提醒。
- 通知应提供 Windows 风格的关闭叉号，用户可以直接关闭当前通知。
- 用户点击通知关闭叉号时，按“跳过本次”处理。
- 通知在没有用户操作的情况下自行消失时，按“延迟”处理：把当前提醒的剩余时间设为全局统一的延迟时长，之后再次发送同一次提醒。
- 通知横幅自行消失后，未被用户处理的通知仍应保留在 Windows 通知中心，而不是被程序当作已读通知删除；保留的通知继续提供原有操作，让用户在下一次提醒出现前仍可处理本次提醒。
- 用户点击通知中心内保留通知的正文时，程序应重新弹出该提醒横幅，使“完成”“延迟”“跳过本次”按钮再次可见；正文点击本身不完成、不延迟也不跳过事件。
- 程序必须区分用户点击关闭叉号和通知自行消失：叉号走跳过逻辑，自动消失走延迟逻辑。
- 通知自动消失时间不再按事件单独设置，改为设置页面中的全局统一设置，默认值为 10 秒。
- 通知中的“延迟”按钮默认延迟 5 分钟；设置中可以修改这一统一时长，但不能为单个事件分别设置不同的延迟时长。
- 用户通过通知按钮执行操作时，程序只处理对应提醒动作，不显示主面板。
- 恢复时发送的“已跳过”通知是纯信息通知，不提供“完成”“延迟”或“跳过本次”等操作按钮。
- “已跳过”通知不显示每个事件错过了几次，也不显示下一次提醒时间。
- 循环事件仍应在程序内部计算后续提醒时间，以便继续调度；“不显示下一次提醒时间”仅限制通知内容。
- 多个不同事件的错过信息合并在一条“已跳过”通知中。
- 如果多个正常运行中的事件恰好在同一时间到点，则每个事件分别发送一条普通提醒通知，不因时间相同而合并。
- 通知的布局、按钮排列和整体视觉使用 Windows 系统原生样式，不自行重新设计通知外观。
- Windows 原生通知的整体背景色和文字颜色由系统控制，不提供每条事件任意选择通知颜色的属性。
- Windows 11 允许的绿色 `Success`、红色 `Critical` 按钮属于有限的操作语义样式，不作为事件通知颜色选择器。

### 3.8 版本显示与新版本检查

- 程序主页应显示当前版本号。
- 版本号显示在主页左上角，位于程序图标旁或程序名称旁，不再单独放在右上角。
- 当前版本号为 `0.4.1`。
- 版本号使用三段式规则：
  - 第一位为主版本号，在发生重大架构重构时增加；
  - 第二位为子版本号，在上线新功能时增加；
  - 第三位为修复号，在当前版本内修复 Bug 时增加。
- 检测到新版本时，在版本号旁显示 `new`。
- 除版本号旁的 `new` 外，不使用其他提示打扰用户。
- `new` 标记可以点击。
- 用户点击 `new` 后，显示提示框，说明当前存在新版本并询问是否更新。
- 更新提示框应尽量展示新版本的更新内容。
- 用户确认更新后，程序应自动下载新版本、自动安装，并用新版本替换当前程序。
- 用户确认更新后，程序先下载并校验新版安装程序，再保存当前运行状态并退出主进程，由新版安装程序完成覆盖安装。
- 覆盖更新只替换程序文件，不得覆盖或删除软件目录内的 `Data` 数据目录；更新完成后自动重新启动 Reminder。
- 新版安装程序下载期间使用的文件也应位于软件目录内的相对 `Data` 目录，不在其他位置静默留下更新文件。
- 新版本检查需要联网，但不应持续联网。
- 程序在一天中首次启动时检查一次新版本；同一天后续再次启动不重复检查。
- 联网或版本检查失败时不提醒用户。
- 用户已经确认更新后，如果自动下载、安装或替换过程失败，程序应显示软件内提示页面并说明“更新失败”；这与后台版本检查失败时保持安静是两种不同情况。
- 版本信息的最终来源尚未确定。当前初步方向是将软件版本发布在 GitHub，版本检查信息可能来自 GitHub 或单独的服务器。

### 3.9 主题与外观

- 程序支持浅色主题和深色主题。
- 浅色主题整体采用白色。
- 深色主题整体采用暗色。
- 用户可以手动选择主题，也可以设置为跟随系统主题。
- 主题默认选择“跟随系统”。
- 主题切换不需要额外的特殊交互规则，但必须根据背景正确调整字体颜色，保证文字清晰可读。
- 界面不应显得古老，应具有简洁、简约、干净和高级的视觉感受。
- UI 保留 Windows 的交互方式和高级感，但不要求完全复刻 Windows；颜色、卡片表面和其他视觉细节可以形成 Reminder 自己的风格。
- 当前视觉方向采用冷灰底色和低饱和靛蓝主色：浅色界面以浅冷灰页面和白色卡片形成层次，深色界面使用炭黑色系而非纯黑。
- `0.0.0` 初步简易版本只实现上述方向的单一浅色主题，不实现主题切换；完整版本仍按既有需求支持浅色、深色和跟随系统。
- 按钮保留清晰的悬停、按下、禁用和键盘焦点反馈，并使用克制、快速的过渡动画，不使用明显弹跳效果。
- 鼠标在“全部重启”按钮上停留 1 秒后，按钮上方显示“重启所有已开启事件的倒计时”。
- 鼠标在全局切换按钮上停留 1 秒后，根据当前状态分别显示“暂停所有已开启事件的倒计时”或“继续所有已开启事件的倒计时”；按钮由“全部暂停”切换为“全部恢复”或反向切换时，立即清除已经显示的旧提示。
- 事件开启/关闭滑块切换时，滑块应流畅移动到另一侧，不直接跳变。
- “添加事件”使用主色填充按钮；合并后的全部暂停/全部恢复按钮和全部重启使用次级按钮；卡片内操作使用紧凑按钮；删除按钮和删除确认按钮始终使用明确的红色填充危险状态。
- 删除事件、滚动、自动定位及以后新增的其他界面动画都必须同时兼顾流畅性和低资源占用；动画只在实际发生交互时短暂运行，结束后不保留空闲计时或持续刷新。
- 界面动画不得固定按 60 帧或其他预设帧数生成。动画应以持续时间和实际经过时间推进，并在系统条件允许时跟随 WPF 与 Windows 桌面合成器当前提供的实际渲染节奏；高刷新率屏幕可以自然呈现更多中间画面。
- 电脑连接多台刷新率不同的显示器，或窗口在不同刷新率显示器之间移动时，动画的总时长和运动速度应保持一致，不以主显示器刷新率或固定的 `1/60` 秒步长推进。
- 实际呈现帧率可能受 Windows 合成、系统负载、硬件和驱动影响，因此程序不承诺始终等于显示器标称刷新率；要求是程序自身不设置固定 60 帧上限，并适应系统实际提供的渲染时机。

### 3.10 事件卡片布局

- 事件列表中的每条事件使用独立的带底框区域显示。
- 单条事件内部横向排列字段，并提供横向滚动条，以适应非全屏窗口。
- 默认窗口大小和系统默认缩放比例下，单条事件的全部字段应无需横向移动即可显示；横向滚动能力仍保留，用于更小窗口或用户采用其他缩放比例的情况。
- 动态表单中的各功能位置按照该位置可能出现的最大内容预留空间，切换事件类型或频率时不应造成后续模块明显左右跳动。
- 每条事件分为上下两行。
- 暂停或关闭的非活动事件整体显示得更淡，以区别仍在活动的事件。
- 正常运行事件的名称下方使用亮浅绿色显示“运行中”，作为轻量的活动状态提示；其他状态仍使用各自的普通或错误颜色。
- 第一行当前包含：
  1. 可直接编辑的事件名称文本框；
  2. 在“暂停”和“恢复”之间切换的按钮；
  3. 仅固定时间事件显示的“重启”按钮；
  4. 只读倒计时；
  5. 开启/关闭滑块；
  6. 删除操作。
- 第二行当前包含：
  1. 事件类型滑块及随类型变化的时间表单；
  2. 息屏和锁屏策略表单。
- 事件类型滑块左侧为“固定时间事件”，右侧为“指定时间事件”，新建自定义事件默认选择左侧。
- 固定时间事件的动态表单显示提醒间隔和终止次数。
- 指定时间事件的动态表单显示频率和随频率变化的指定时间字段；频率不是“仅一次”时还显示终止次数，选择“仅一次”时隐藏终止次数设置。
- 固定时间事件第一行共六个功能位置；指定时间事件不显示暂停/恢复和重启，只显示名称、倒计时、开启/关闭和删除。
- 程序页面底部不显示“关闭窗口后仍会在后台计时，可双击系统托盘图标重新打开”提示；底部使用较薄的状态栏，并在右下角显示 Windows 通知状态。
- Windows 通知正常时，右下角显示“Windows 通知已就绪”；通知权限、系统策略、安装声明或通知组件错误导致不可用时，显示红色的“Windows 通知未就绪”。鼠标悬停未就绪状态时应显示具体原因和对应解决办法。
- 程序每次启动时必须主动检测一次 Windows 通知权限和就绪状态，使启动界面直接显示当前结果；运行期间继续在每次发送通知时复检，并在投递失败后及时转为未就绪。
- 程序采用顶部结构，不设置占用较多横向空间的宽侧边栏。
- 页面顶部左侧显示程序图标、名称、版本号和标语；窗口视觉中心显示“主页”“事件”“设置”三个顶级导航选项。当前不为未确认的功能增加更多顶级页面。
- 顶部第二层作为页面操作区。主页和事件页共用合并后的全部暂停/全部恢复按钮与全部重启，事件页额外显示添加事件；设置页不显示这些提醒操作。
- 事件页不再显示“提醒事件”大标题，可以使用较弱的事件总数和运行中数量摘要。

### 3.11 表单输入校验

- 所有允许用户自定义输入的表单都必须检查输入是否合法。
- 输入必须在被接受、保存或用于提醒计算前通过校验，程序不能直接使用未经检查的用户输入。
- 非法、异常或过大的输入不得造成数值溢出、程序崩溃或错误的运行状态。
- 校验失败的输入不得应用到事件或全局设置中。
- 校验失败的临时输入不得进入 Logic 或持久化状态，也不得触发该字段的即时保存；即使非法文本仍停留在界面中，其他操作触发的即时保存或约一小时自动保存也只能写入该字段最后一次合法值。
- 各输入字段的具体格式、长度和数值范围上限等待后续逐项确定。
- 事件名称达到 50 个加权字符上限后，继续输入会被直接阻止，不在输入超限内容后再显示长度错误；ASCII 权重为 1，非 ASCII 权重为 2。
- 用户首次点击或通过键盘进入文本输入框时，光标默认位于已有字段内容末尾。
- 终止次数以及其他下拉菜单在收起状态下不得使用鼠标滚轮直接切换选项；位于事件列表中的收起下拉框不应阻断主页正常滚动。
- 终止次数以及其他下拉菜单展开后，弹出列表应显示可用的纵向滚动范围；鼠标位于弹出列表中时，滚轮滚动选项列表而不滚动主页。
- 有下拉菜单处于展开状态时，如果用户把鼠标移到主页并滚动，程序应先自动收起该下拉菜单，再执行主页滚动。

### 3.12 主页与多页面导航

- 未来程序主页与事件页分离：主页用于集中查看最近提醒，事件页继续承载当前双行事件卡片列表和完整配置。
- 主页中心使用固定位置的大型圆形计时器，内部显示当前目标事件名称和剩余时间；圆形可以点击并进入对应事件。
- 主页内容是现有事件状态的只读展示映射，不建立或修改另一套事件、计时器、调度状态或业务数据。
- 圆形右侧显示最多三个最近发生的正在计时事件，使用能够容纳较长名称的长方形卡片。
- 一张卡片使用中间槽位，两张卡片使用上下对称槽位，三张卡片使用上、中、下槽位；三个槽位沿圆形右侧圆弧排列，中间槽位比上、下槽位更向右突出。
- 最近事件按剩余时间升序排列；剩余时间相同时，事件列表中位置更靠上的事件优先。
- 用户手动单项暂停或关闭的事件不进入主页最近事件候选。
- 鼠标指向右侧卡片时，圆形临时显示该事件；离开卡片区域后恢复显示最近事件。指向状态使用底色、边框或阴影表达选中感，不移动卡片固定位置。
- 点击右侧卡片或圆形后进入事件页，自动滚动到对应事件并使用与新增事件相同的短暂高亮。
- 圆形周围从内向外使用秒、分、时、天圆环，分别以 60 秒、60 分、24 小时和 365 天为一圈；这些圆环表示剩余时间分量，不表示总周期完成比例。
- 圆环只绘制表示当前时间分量的彩色部分，不绘制较淡的完整背景轨道；圆环从十二点方向开始顺时针绘制并使用圆头端点。
- 倒计时超过 365 天时，天环显示总天数除以 365 后的余数，并在外侧只增加一个完整圆环；中心文字仍显示真实总天数。回到 365 天时额外圆环消失，基础天环显示满圈。
- 时间分量减少时，圆环使用带自然加速和减速的快速过渡；分量从最小值回到接近满值时使用快速涨满动画。
- 主页倒计时采用适应剩余时长的格式：不足一小时以分、秒为主，不足一天显示时、分、秒，一天以上以总天数为主并辅助显示时、分、秒。
- 全部暂停期间主页不清空最近事件。固定时间间隔事件显示冻结的剩余时间；指定时间事件继续显示距离真实计划时刻的时间并标记“暂停中，到点不提醒”，计划已经发生后显示“暂停期间已发生”，恢复时再进入“已跳过”汇总。
- 已经到点并等待用户处理的普通提醒保持最高展示优先级，圆形显示“等待处理”；主页不提供通知处理按钮。
- 没有任何正在计时事件时保留圆形位置，中心显示“暂无正在计时的事件”，不显示空圆环轨道；点击后进入事件页但不定位具体事件。
- 全部暂停或全部恢复改变候选集合、顺序或内容时，从最新事件状态重新计算只读映射，并使用短暂卡片强调和圆形膨胀过渡。
- 主页与事件页切换时，事件列表整体从下向上进入或向下离开，添加事件按钮随事件页从右向左出现或向右消失；共用的全局按钮保持稳定。
- 事件页与设置页切换时，事件列表和页面操作散去后设置内容淡入，反向切换采用相反过程；主页与设置页之间使用更快的普通淡入淡出。
- 通过顶级导航正常进入事件页时保留上一次滚动位置；从主页具体事件进入时，目标定位覆盖该滚动位置。
- 页面切换期间的连续导航以最后一次选择为目标，不排队播放多次完整动画。
- 当前已经确认的主页与多页面导航实施阶段中，设置页只建立页面容器、顶部导航入口和页面切换能力；本阶段不加入任何设置条目、设置数据或设置业务逻辑。

### 已确认的初步交互想法

以下内容是用户已经提出的初步交互方向，后续仍可调整：

- 提醒事件采用列表形式展示，每个事件使用带底框的两行卡片。
- 每条事件支持横向滚动。
- 固定时间事件第一行显示名称、暂停/恢复、重启、倒计时、开关和删除；指定时间事件不显示暂停/恢复和重启。
- 第二行使用滑块切换“固定时间事件”或“指定时间事件”，并显示对应参数及息屏、锁屏策略。
- 对功能上多选一、彼此互斥的设置，可使用滑块控制当前选项，再配置该选项对应的内容，使用户不必自行判断哪些功能相互冲突。
- 每个事件的展示应保持简洁明了。

## 4. 非功能需求

### 4.1 轻量化

- 轻量化是本项目的重要目标。
- 程序预计长期在后台运行，应尽可能降低后台内存占用。
- 应尽可能降低 CPU 占用。
- 空闲时不应频繁轮询。
- 提醒功能不应明显影响电脑性能。
- 应避免为了简单功能引入过于庞大的依赖或运行环境。
- 以配备 16 GB 内存的电脑作为当前资源目标参考环境。
- 主界面显示时，内存占用目标为 160 MB 以下。
- 主界面关闭、程序仅在后台运行时，内存占用目标为 100 MB 以下。
- 无论主界面是否显示，CPU 占用目标均为 1% 以下。
- 安装包大小没有严格限制，当前以不超过 300 MB 为可接受目标。
- 上述数值是允许一定弹性的优化目标，不作为任何轻微超出即判定软件不可用的硬性门槛；应尽量满足更多目标，并在功能和稳定性不受损的前提下尽可能降低资源占用。
- 界面动画不得通过长期运行的高频轮询维持。动画只处理当前可见且确实发生变化的元素，并应尽量避免逐帧触发布局重算；用户关闭 Windows 界面动画时，应直接完成操作而不影响功能结果。
- 高刷新率显示器允许短时交互动画产生更多渲染画面；这部分工作只能在动画可见期间按需发生，不能形成窗口空闲或隐藏后的持续资源占用。

### 4.2 稳定性

- 程序长时间运行时需要保持稳定。
- 程序需要正确面对睡眠、休眠、唤醒、锁屏、解锁、息屏和亮屏等 Windows 使用状态。
- 系统时间或时区发生变化时，程序应继续依据当前时间、事件计划和事件开关状态进行调度，不要求维护额外的时区变更历史，也不应因此崩溃。

### 4.3 克制与低打扰

- 程序不应持续显示主窗口或占用桌面空间。
- 通知应自然、克制，不使用突兀或遮挡屏幕的交互。
- 新版本检查失败不应弹出错误提示。
- 用户已经确认更新后，如果下载或安装更新失败，应显示软件内“更新失败”提示页面。
- 检测到新版本时只显示轻量的 `new` 标记，不额外提醒。

### 4.4 易用性

- 软件不提供新手引导，因此界面和设置必须简洁明了。
- 互斥选项的呈现应帮助用户理解当前选择，避免要求用户自行判断设置冲突。

### 4.5 视觉风格

- 界面整体追求简洁、简约、干净和高级。
- 视觉感受可参考 Clash Verge 的程序面板，但不要求复制其具体界面。

### 4.6 可维护性与可扩展性

- 初期测试版本的代码架构也应结合当前已经确认的功能和未来功能扩建需要进行设计。
- 测试版本不应采用只能一次性验证、后续难以扩展的临时代码结构；其代码应能够作为后续正式实现的基础继续演进。
- 所有数据交互和状态变更流程都应保留可扩展边界，使未来增加事件类型、字段、操作、设置或平台返回结果时，不必重写无关模块。
- 界面提示与动画、提醒业务状态、Windows 平台回调、存储与网络交互应继续由各自模块负责，并通过明确的方法、事件或接口传递意图与结果。
- 可复用交互应抽取为小型通用组件，不把业务状态修改硬编码到视觉控件或 Windows 回调中；同时不为尚未确认的功能提前引入庞大框架。
- Reminder 的程序代码初步采用一个 WPF 项目，不把不同职责分别拆成多个独立的 Visual Studio 项目。
- 该项目内部划分为四个主要模块：
  1. `UI` 界面设计模块；
  2. `Logic` 计算逻辑模块；
  3. `Windows` 交互模块，负责系统状态检测、系统通知等 Windows 功能；
  4. `System` 系统模块，负责配置与运行状态存储、联网检查版本和自动更新，承担程序运行时与网络和硬盘的交互。
- 模块间不设置僵硬的单向调用限制；各模块在遵守自身职责的前提下，可以按实际需要使用其他模块提供的数据或功能。
- `UI` 模块可以按显示需要读取相应数据；需要持续刷新显示的数据可以使用 WPF 数据绑定。
- 需要更改的提醒业务数据由 `Logic` 模块处理。
- `Windows` 模块检测到 Windows 活动后通知 `Logic` 模块；`Logic` 完成相应的数据处理后，由 `UI` 模块显示更新结果。
- 调度逻辑不直接操作界面。
- 调度逻辑不直接调用 Windows 通知代码，而是通过 `Windows` 模块提供的边界触发通知。
- 界面不直接修改后台计时器，而是把用户操作交给 `Logic` 模块处理。
- 不建立巨大的全局变量池；各模块维护自身状态，需要其他模块的数据时按需读取。
- 只有版本号等全局固定信息可以作为全局共享数据，并且运行期间不可更改。
- 四个模块内部的具体目录和更细的职责边界等待后续架构讨论继续明确。

### 已确认的初步实现约束

- 提醒功能优先考虑 Windows 自带的系统通知机制。
- 桌面界面和应用生命周期先采用 WPF 实现。
- 后台调度采用事件驱动方式，避免空闲时频繁轮询。
- 后台只持续维护最近一个即将到期的提醒时间，使用一个计时器等待最近到期事件，不为每个事件运行持续检查循环。
- 当事件配置、完成、延迟、跳过、暂停、恢复或系统状态发生变化时，重新计算最近到期事件。
- 主面板显示时，另外使用一个轻量 UI 刷新计时器更新倒计时文字；该计时器只负责显示，不承担提醒调度。
- 主面板隐藏时停止逐秒刷新倒计时界面。
- 只有主面板可见时，才按界面展示需要刷新倒计时文字。
- 版本检查使用低频异步任务；检查失败时安静结束，不持续重试或弹出错误。
- 依赖和运行环境的选择需要考虑长期后台运行的资源成本。

### 4.7 发布与运行环境

- 开发阶段可以使用框架依赖方式，以缩短构建和测试流程。
- 正式发布只考虑自包含方式，不发布要求用户预先安装对应 .NET 运行时的框架依赖版本。
- 自包含发布必须带齐运行所需依赖，不能因目标电脑缺少开发环境或运行时而无法启动。
- 正式发布采用 Inno Setup 生成的自包含 `.exe` 安装程序，不再采用 MSIX 或 Windows App Installer。
- 安装程序必须允许用户自行选择安装目录，包括选择非系统盘目录；Reminder 不得强制安装到 C 盘。
- 安装程序负责创建程序文件、相对 `Data` 数据目录、快捷方式和卸载入口，并在 Windows 的应用管理中注册可正常执行的卸载程序。
- 如果用户选择的安装位置属于受保护目录，安装程序只能为独立的 `Data` 子目录配置运行所需写权限，不得让普通用户获得修改程序文件目录的权限。
- 软件内更新模块负责检查、下载和校验新版安装程序；用户确认后，更新模块调用 Inno Setup 的静默覆盖安装能力完成更新。
- 覆盖安装必须复用原安装目录，只替换程序文件并保留 `Data`；完成后自动重新启动 Reminder。
- 初始发布不提供便携压缩包版本。
- 安装后的程序必须能够通过 Windows 的应用管理入口正常卸载；卸载开始前必须询问用户选择“保留 Data”或“删除 Data”。
- 用户选择“保留 Data”时，卸载程序仅移除程序文件、快捷方式和卸载注册等安装内容，保留完整的 `Data` 目录。
- 用户选择“删除 Data”时，卸载程序同时删除完整的 `Data` 目录。
- 正式发布流程需要配置软件标识、版本、安装包签名和可信更新来源；更新包必须在执行前通过完整性或签名校验。

### 4.8 输入安全

- 程序必须对所有用户自定义表单输入执行合法性检查，防止异常输入被直接用于解析、保存或计算。
- 输入处理不得因非法格式、异常长度或过大数值产生溢出攻击风险、程序崩溃或状态损坏。

## 5. 用户使用流程

### 5.1 启动程序

1. 用户手动启动程序，或选择让程序随 Windows 开机自动启动；当天第一次启动时，程序在后台执行一次新版本检查。
2. 如果启用了静默启动，程序直接在后台运行，不显示程序面板。
3. 程序进入后台后，通过系统托盘图标提供持续入口。

### 5.2 在主页查看最近提醒

1. 用户打开非静默启动的程序面板或通过托盘进入主页。
2. 主页圆形默认显示距离发生最近的正在计时事件，右侧最多列出三个最近事件。
3. 用户把鼠标移到其他最近事件卡片时，可以在圆形中查看该事件名称、倒计时和多层时间圆环。
4. 用户点击圆形或右侧卡片后进入事件页，列表自动定位并高亮对应事件。
5. 用户可以直接在主页使用全部暂停/全部恢复和全部重启；全部暂停期间主页保留暂停事件及其剩余时间状态。

### 5.3 查看和配置提醒事件

1. 用户打开程序面板。
2. 首次使用时，用户可以看到默认关闭的“喝水”和“休息眼睛”示例事件；也可以查看其他自定义事件和各事件的倒计时。
3. 用户点击“添加事件”后，列表立即新增一条名称为“新建事件”的默认事件；该事件默认开启、不暂停、采用 45 分钟的固定时间事件，并默认不终止。
4. 程序在内部为每条事件保存不展示的 `event id`，用它区分同名事件。
5. 用户可以单独启用或禁用事件。
6. 用户通过第二行的滑块选择“固定时间事件”或“指定时间事件”，并配置该模式所需的固定间隔、指定提醒时间、提醒频率、终止次数和其他参数；表单字段随事件类型和循环频率变化，指定时间事件选择“仅一次”时不显示终止次数。
7. 用户按需配置固定时间间隔事件在息屏和锁屏期间继续计时、重新计时或暂停计时，并在继续计时时选择是否在该期间发送普通提醒。
8. 用户按需配置指定时间与频率事件在息屏和锁屏期间采用“提醒”，或者暂不提醒并在恢复后提示“已跳过”。
9. 实际睡眠或休眠不提供用户设置；从睡眠或休眠唤醒后，期间到点的事件按“已跳过”处理。
10. 用户把事件开关从开启切换为关闭时，程序复用暂停逻辑；固定时间事件直接拨回开启时保留已有单项暂停，指定时间事件拨回开启时恢复日历调度；用户成功修改关闭事件的设置后，事件自动开启并解除单项暂停。
11. 用户可以保存位于过去的指定时间；程序按照一次性或循环规则判断下一步处理。
12. 用户可以删除两个初始示例事件，也可以添加或删除自定义事件；删除前必须在确认框中点击“确定”，点击“取消”不改变事件。

### 5.4 接收和处理提醒

1. 事件到达提醒时间时，程序优先通过 Windows 系统通知发送对应提醒。
2. 用户直接在通知中选择“完成”“延迟”或“跳过本次”。
3. 用户点击“完成”后，该事件从完成时刻开始计算下一轮提醒时间。
4. 用户选择延迟时，程序把当前剩余时间直接改为设置中的统一延迟时长；默认值为 5 分钟，该倒计时结束后再次提醒。
5. 用户点击通知右上角的 Windows 关闭叉号时，当前通知关闭，并按“跳过本次”处理。
6. 通知到达全局设置的自动消失时间后自行消失时，按“延迟”处理；默认自动消失时间为 10 秒，当前提醒随后按照全局延迟时长再次出现。
7. 程序区分关闭原因：点击叉号走跳过逻辑，自动消失走延迟逻辑。
8. 用户通过通知按钮处理提醒时，程序不显示主面板。
9. 事件在息屏或锁屏期间是否发送普通提醒，按照事件类型和用户为该状态选择的策略处理；显示器已关闭且策略要求提醒时，程序请求点亮锁屏画面后发送通知；实际睡眠或休眠期间不发送提醒。
10. 当程序恢复运行、用户解锁、对应事件没有单项暂停且全部暂停已经结束时，程序汇总符合条件的错过提醒。
11. 同一事件错过多次只汇总一次；多个不同事件合并为一条纯信息“已跳过”通知，通知列出事件名称但不显示错过次数或下一次提醒时间。发送汇总时，其中每个不同事件分别扣减 1 次终止次数。
12. 多个普通事件在同一时间到点时，每个事件仍分别发送一条带操作按钮的普通通知。

### 5.5 控制计时状态

1. 用户可以暂停或恢复单个事件。
2. 用户通过同一个切换按钮暂停或恢复全部已开启事件。
3. 开启全部暂停后，用户可以保持默认的“直到手动恢复”，也可以选择 1 分钟、5 分钟、10 分钟、15 分钟、30 分钟、1 小时、2 小时或 5 小时。
4. 选择具体时长时，用户可以看到暂停剩余时间；选择手动恢复时不显示倒计时。
5. 全部暂停结束后，所有已开启固定时间间隔事件解除单项暂停，并从各自冻结的剩余时间继续。
6. 用户可以重启符合条件的单个固定间隔事件；执行全部重启时，所有已开启固定时间间隔事件解除单项暂停、清除已经经过的本轮时间，并从 `0` 开始一个完整间隔。
7. 指定时间与频率事件在暂停期间到点时记为已跳过，等满足恢复条件后统一提示。

### 5.6 关闭面板与退出程序

1. 用户关闭可见窗口后，程序继续在后台运行。
2. 用户需要完全退出程序时，通过系统托盘图标右键菜单选择“退出”。
3. 程序在退出前保存当前所有需要恢复的配置与运行状态。
4. 程序未运行期间，固定间隔、经过延迟调整的当前剩余时间和限时全部暂停的倒计时全部冻结。
5. 下次启动时优先读取事件及其保存状态，再从退出时保存的剩余时间恢复固定间隔和限时暂停计时。
6. 对程序未运行期间到点的指定时间与频率事件，等满足恢复条件后汇总发送一次“已跳过”，然后按照事件原有规则继续调度。
7. 退出时尚未被用户处理的普通提醒按已跳过处理，并在下次满足恢复条件时加入汇总通知。
8. 如果正式状态文件 `Data\state.dat` 损坏或无法载入，程序自动尝试从 `Data\state.bak` 恢复。
9. 如果 `state.bak` 也无法恢复，程序打开一个独立提示窗口，显示状态恢复失败。
10. 恢复失败提示窗口提供确认操作；用户确认后关闭该提示窗口。

### 5.7 查看并安装新版本

1. 程序在一天中首次启动时检查一次是否存在新版本。
2. 检测到新版本后，只在主页版本号旁显示可点击的 `new` 标记。
3. 用户点击 `new` 后，查看新版本提示和更新内容，并决定是否更新。
4. 用户确认后，程序自动下载、安装并替换为新版本。
5. 如果用户确认后的更新过程失败，程序显示软件内“更新失败”提示页面。

### 5.8 卸载程序

1. 用户通过 Windows 的应用管理入口或安装目录中的卸载程序开始卸载。
2. 卸载开始前，必须询问用户选择“保留 Data”或“删除 Data”。
3. 选择“保留 Data”时，卸载程序移除程序本体、快捷方式和卸载注册等安装内容，但保留完整的 `Data` 目录。
4. 选择“删除 Data”时，卸载程序在移除程序内容的同时删除完整的 `Data` 目录。

### 已确认的初步流程想法

- 事件配置以“一条事件一个带底框的双行卡片”呈现，并允许横向滚动。
- 对互斥的提醒方式先进行选择，再显示相应的具体设置，减少同一行中同时出现互相冲突的配置。

## 6. 配置与数据存储

### 6.1 已确认需要配置的信息

- 当前事件列表，包括初始示例事件或用户自定义事件，以及每个事件的启用状态。
- 每条事件内部唯一且不向用户展示的 `event id`；事件名称不承担唯一标识作用。
- 每个事件独立的开启或关闭状态，以及与其分开保存的暂停属性。
- 每个事件的名称和提醒方式。
- 每个事件的固定提醒间隔。
- 每个适用事件的终止次数或“不终止”，以及选择有限次数时的当前剩余次数；指定时间事件选择“仅一次”时不显示该设置。
- 采用指定时间与频率模式时的指定提醒时间，以及“一次性”“每天”“每周”“每月”或“每年”的频率设置。
- 固定时间间隔事件在息屏或锁屏时共同采用继续计时、重新计时或暂停计时的设置。
- 固定时间间隔事件采用继续计时策略时，在息屏或锁屏期间是否发送提醒的设置。
- 指定时间与频率事件在息屏或锁屏期间采用“提醒”或“不提醒”的设置。
- 是否开机自动启动。
- 是否静默启动。
- 全局统一的通知延迟时长，默认值为 5 分钟。
- 全局统一的通知自动消失时间，默认值为 10 秒。
- 当天是否已经执行过首次启动版本检查所需的状态。
- 浅色、深色或跟随系统的主题设置。

### 6.2 运行期间的状态

程序运行时需要维护各事件相互独立的计时和当前剩余时间，事件的开启或关闭状态，单个事件和全部事件的暂停、恢复与重启状态，限时全部暂停的剩余时间，以及已经发生但尚待恢复提示的错过提醒。

“延迟”操作直接修改事件当前剩余时间，不保存独立的延迟状态。已经结束的一次性事件在提示“已跳过”后切换为关闭，程序依靠当前时间、计划规则和开关状态避免重复处理，不为该次计划保存额外的“已处理”字段。

用户通过托盘菜单主动退出时，应保存所有用于恢复当前配置、事件计时和暂停状态的必要数据。新建、删除或成功修改事件设置后，执行全部暂停、全部恢复或全部重启后，以及设置或更改全部暂停限时时长后，应立即在后台保存最新完整状态；紧邻发生的保存请求可以合并，但不得丢失最终状态。正常运行期间仍约每 1 小时低频保存一次状态，具体间隔无需精确。设置完成后全部暂停倒计时的继续流逝，以及单项暂停、单项恢复、单项重启、完成、延迟、跳过和其他单纯倒计时流逝，不要求每次立即写入磁盘。异常退出或系统意外终止时，允许这些运行状态恢复到最近一次即时保存或低频保存的结果，并接受由此产生的小幅提醒节奏变化。

### 6.3 存储方案

- 最终持久化数据不得直接以可读明文形式存取，目标是避免用户直接查看或修改文件内容。
- 存储方案需要能够发现并拒绝使用被篡改或无法通过完整性检查的数据，避免错误数据进入提醒调度。
- 在满足非明文和篡改检测要求的同时，应保持读取、写入和启动恢复足够轻量。
- 未来持久化采用版本化 JSON 数据结构；数据先由 `System.Text.Json` 序列化为 UTF-8 字节，再使用 Windows DPAPI 以当前 Windows 用户范围整体保护，最后作为非明文二进制文件保存。
- 受保护数据必须通过 DPAPI 的完整性检查后才能反序列化并交给提醒逻辑；解密或完整性检查失败的数据不得载入。
- JSON 内部保存独立的数据结构版本，用于未来字段变更和迁移；数据结构版本不直接等同于应用版本号。
- 写入时采用临时文件完成写入后再原子替换正式文件的方式，避免中断写入破坏唯一状态文件；必要时保留一个可恢复备份。
- 存储保护采用当前用户范围，因此数据主要绑定当前 Windows 用户及本机环境。用户配置文件丢失、系统重装或迁移到其他用户与电脑后，原数据可能无法解密；Reminder 的本地提醒配置接受这一限制。
- 所有由 Reminder 自身产生的运行数据、状态文件、备份、原子写入临时文件和更新下载文件，都必须位于软件自身目录内的相对 `Data` 文件夹中，不得改用 `%AppData%`、`%LocalAppData%` 或其他 C 盘位置进行静默存储。
- 路径必须以 Reminder 可执行程序的实际所在目录为基准解析，不依赖进程当前工作目录。
- 当前确认的基础文件布局为：
  - `Data\state.dat`：正式受保护状态；
  - `Data\state.bak`：可恢复备份；
  - `Data\state.tmp`：原子写入过程中的临时文件；
  - `Data\Updates\`：软件更新安装包的临时保存目录。
- `state.dat` 损坏、解密失败、完整性检查失败、无法解析、版本不受支持或字段校验失败时，不得把其中的数据交给提醒逻辑，并应自动尝试载入 `state.bak`。
- 如果 `state.bak` 也无法恢复，程序必须打开独立的恢复失败提示窗口；用户确认后关闭该提示窗口。
- 覆盖更新不得删除或替换 `Data`。备份触发条件和数据结构迁移细节继续在持久化阶段确定。

### 初步想法

存储格式、保护方式、基础文件组织和备份恢复顺序已经确定；具体状态文档字段、备份生成时机和旧数据迁移规则在实际持久化阶段进一步闭环。

## 7. 初步简易版本范围

### 7.1 目标

- 初步简易版本只实现简单 UI 和最小可运行逻辑，但代码结构必须能够继续扩展为完整版本。
- 首版应真正打通一个固定时间间隔事件的核心运行闭环，不做只有界面、没有实际行为的空壳演示。
- 当前版本号为 `0.4.1`。

### 7.2 首版实现范围

- 显示初步主页面和事件卡片列表。
- 提供默认关闭的“喝水”和“休息眼睛”示例事件。
- 支持添加和删除自定义固定时间间隔事件。
- 支持编辑事件名称和固定提醒间隔，并执行输入合法性校验。
- 支持事件开启、关闭、暂停、恢复和重启。
- 支持基础的全部暂停、全部恢复和全部重启。
- 显示精确到秒的事件倒计时。
- 主面板隐藏后，固定时间间隔事件继续在后台运行；再次显示主面板后恢复倒计时文字刷新。
- 到点时发送真实的 Windows 系统通知。
- 通知中的“完成”“延迟”和“跳过本次”能够处理固定时间间隔事件。
- 首版验证 Windows 通知接口能否准确区分用户点击关闭叉号和通知自动消失，并记录验证结果。
- 代码继续遵守 `UI`、`Logic`、`Windows`、`System` 四模块职责，以及调度、界面和通知之间的三个边界。
- UI 采用已经确认的 Windows 交互基础、Reminder 自定义色彩和顶部页面结构。

### 7.3 首版暂不实现

- 指定时间事件及每天、每周、每月、每年循环。
- 终止次数、息屏或锁屏策略、睡眠或休眠后的错过汇总和完整离线恢复规则。
- 限时全部暂停、开机启动、静默启动、版本检查、自动更新和正式 Inno Setup 安装程序发布。
- 数据保存、下次启动恢复数据和异常退出恢复。
- 完整退出程序的功能。
- 浅色、深色和跟随系统之间的主题切换。

### 7.4 当前与后续实施顺序

- 初步简易版本成型后，优先继续完善事件类型、事件表单、提醒调度和事件相关状态处理。
- 完整事件时间模型阶段已经确认实现以下范围：
  1. 建立固定时间事件和指定时间事件的共同数据结构；
  2. 实现事件类型切换和动态表单；
  3. 实现仅一次、每天、每周、每月和每年；
  4. 实现“不终止、1–100 次”的终止次数；
  5. 两类事件共用最近到期调度器、通知操作和倒计时；
  6. 完成日期、时间和次数等输入校验；
  7. 回归跨日、跨月、闰年、缺失日期和过去时间等边界；
