# Reminder 提醒逻辑细节

- 文档状态：持续讨论与迭代
- 最近更新：2026-07-27
- 关联主文档：`docs/REQUIREMENTS.md`

本文档记录已经确认、但放在主需求文档中会显得过于琐碎的提醒状态、恢复规则和时间边界。它是需求文档的细化说明，不是另一套独立需求。后续确认的规则如果与本文档冲突，应采用最新确认的规则，并同步修正两份文档。

## 1. 基本概念

### 1.1 两种时间模式

1. **固定时间间隔事件**
   - 从设置生效时开始倒计时。
   - 到点后按照固定间隔继续调度。
   - 在需要冻结的状态中保存“当前剩余时间”，恢复后继续该剩余时间。
2. **指定时间与频率事件**
   - 在指定时间产生提醒。
   - 频率可以是一次性、每天、每周、每月或每年。
   - 是否在某段不可提醒状态中错过，需要根据指定计划和该段时间范围判断。

### 1.2 开关与暂停是两个属性

- 每个事件都有独立的开启/关闭开关和暂停属性。
- 从开启直接拨到关闭：事件变为关闭，并复用单项暂停逻辑；如果本来已经暂停，不重复处理。
- 固定时间事件从关闭直接拨到开启：把事件设为开启，同时解除已有单项暂停，并从冻结的剩余时间继续计时，不再要求用户额外点击“恢复”。处于全部暂停时复用既有单项恢复例外，只恢复目标事件。
- 指定时间事件不显示单项暂停按钮，关闭和单项暂停使用同一套操作语义；从关闭拨到开启时恢复日历调度。
- 成功编辑事件名称、时间、类型、频率、终止次数或其他设置：事件自动开启并解除单项暂停，按修改后的设置继续运行。
- 一次性事件完成或错过后：事件保留在列表中，但自动关闭。

### 1.3 真正恢复的条件

等待发送的“已跳过”信息，只有同时满足以下条件时才进入真正恢复：

1. 程序正在运行；
2. 用户已经解锁；
3. 对应事件没有处于单项暂停；
4. 全部暂停已经结束。

不满足条件时继续等待，不提前发送恢复汇总通知。

## 2. 不可提醒状态总表

| 所处状态 | 固定时间间隔事件 | 指定时间与频率事件 |
| --- | --- | --- |
| 软件未运行 | 当前剩余时间冻结，离线时长不计入间隔；启动后从保存的剩余时间继续 | 离线期间到点则记为“已跳过”；启动并满足真正恢复条件后提示，再按原计划继续 |
| 单项暂停或全部暂停 | 当前剩余时间冻结，不在暂停期间产生新的固定间隔到点 | 暂停期间到点则记为“已跳过”；满足真正恢复条件后提示，再按原计划继续 |
| 实际睡眠或休眠 | 不提供用户策略，也不在期间提醒；唤醒后检查是否到过提醒时间，到过则提示一次“已跳过”并保持原有时间节奏 | 不提供用户策略，也不在期间提醒；唤醒后检查期间发生的计划，发生过则提示一次“已跳过”，再按原计划继续 |
| 息屏或锁屏 | 两种状态共用一套设置：继续计时、重新计时或暂停计时；继续计时时另选是否发送普通提醒 | 两种状态共用一套设置：到点时提醒，或者不提醒并在恢复后提示“已跳过” |

实际睡眠或休眠已经从用户可配置项中移除。原先讨论过的睡眠期间“继续计时”“重新计时”“暂停计时”“期间发送提醒”等分支均不再作为需求。

## 3. 固定时间间隔事件

### 3.1 软件退出和暂停

- 用户从托盘主动退出时保存事件当前剩余时间和暂停属性。
- 软件未运行期间，相当于固定间隔倒计时被冻结。
- 如果事件退出前已经暂停，启动后仍然保留暂停。
- 限时全部暂停在软件退出时也冻结其剩余暂停时间，启动后继续该暂停倒计时。
- 单项暂停或全部暂停期间，固定间隔事件不产生新的计划到点记录。
- 单项暂停结束后，从暂停前冻结的当前剩余时间继续，不从完整间隔重新开始。
- 全部暂停结束或用户执行“全部恢复”时，所有已开启固定时间事件都解除单项暂停，并从各自冻结的剩余时间继续。
- 全部暂停期间某个事件通过任何有效状态转换取消暂停时，不按“全部恢复”处理：无论来源是单项“恢复”按钮，还是有效编辑自动开启并取消暂停，都仅让目标事件从冻结的剩余时间继续，其他事件仍保持暂停，全部暂停状态和“全部恢复”入口继续保留。
- 所有取消暂停的入口统一经过同一状态转换；转换完成后检查受本次全部暂停影响的已开启事件中是否还存在暂停事件。只有这些事件都已取消暂停时，全部暂停状态才自动结束，不为每一种界面操作重复维护判断。
- 删除事件会缩小本次全部暂停的参与者集合，因此删除完成后也执行同一项集合核对。如果剩余已开启事件都已经取消暂停，立即结束全部暂停；如果仍有任一事件受全部暂停约束，则继续保留全部暂停和“全部恢复”入口。
- 指定时间事件没有单项暂停/恢复入口；只要仍有指定时间事件处于全部暂停中，上述自动结束条件就不会成立，之后仍通过“全部恢复”或原有全部暂停结束条件统一恢复。
- “重启”与“恢复”不同：重启会清除当前一轮已经经过的时间，使固定间隔事件从 `0` 开始一个新的完整间隔。“全部重启”同时包含“全部恢复”：先结束全部暂停并恢复全部已开启事件，再重启所有已开启固定时间事件；指定时间事件只恢复，不改变原有日历计划。

### 3.2 息屏和锁屏策略

固定间隔事件为息屏和锁屏共同选择一套策略：

1. **继续计时**
   - 原有时间节奏不变。
   - 可以继续选择“发送普通提醒”或“不提醒”。
   - 选择发送时，到点后按照正常提醒处理；如果显示器已经因空闲关闭，程序先发出一次短时显示请求，使锁屏画面重新亮起，但不解锁电脑。
   - 选择不提醒时，如果期间到点，恢复后只提示一次“已跳过”。
2. **重新计时**
   - 对应系统状态结束后，从一个完整的固定间隔重新开始。
3. **暂停计时**
   - 对应系统状态期间冻结剩余时间，恢复后继续该剩余时间。

### 3.3 保持原节奏

固定间隔事件采用继续计时，但在不可提醒期间抑制了普通通知时，恢复后的“已跳过”提示不改变原来的固定节奏。

例如，某事件的计划节奏为 `10:00、10:30、11:00、11:30、12:00`，用户在 `11:45` 恢复：

- 恢复时提示该事件“已跳过”一次；
- 下一次仍为 `12:00`；
- 不从 `11:45` 重新计算到 `12:15`。

“已跳过”通知不显示 `12:00`，但程序内部仍然必须计算下一个未来计划时间，否则循环事件无法继续调度。

### 3.4 完成、延迟与跳过

- **完成**：从用户实际点击完成的时刻开始重新计算下一轮固定间隔。
- **延迟**：直接把当前提醒的剩余时间改成设置中的统一延迟时长。默认是 5 分钟；例如选择延迟后，就把当前剩余时间设为 5 分钟，倒计时结束后再次提醒。
- 延迟时长可以在设置中统一修改，但不能为不同事件设置不同的延迟时长。
- 固定时间间隔事件的实际延迟时长由设置中的策略决定：默认“缩短为事件提醒间隔”时，取全局延迟时长与事件固定间隔中的较小值；选择“仍使用统一延迟时间”时，即使统一延迟长于事件间隔也不缩短。
- 延迟不创建独立的“延迟状态”，也不需要额外的“延迟剩余时间”字段；它使用事件本身的当前剩余时间。
- 如果延迟后的当前剩余时间尚未结束时退出软件，该剩余时间和其他固定倒计时一样冻结并保存，下次启动后继续。
- **跳过本次**：结束当前通知，不把“已跳过”恢复汇总当作另一次可操作提醒；下一轮从本次通知发出的时刻开始计时。
- 点击通知关闭叉号等同于按下“跳过本次”按钮，采用跳过本次的下一轮计时基点。
- 通知自行消失等同于选择“延迟”：通过与通知按钮相同的统一延迟解析规则修改当前剩余时间，之后再次发送同一次提醒。

## 4. 指定时间与频率事件

### 4.1 允许过去时间

- 设置界面不因为指定时间位于过去而拒绝保存。
- 循环事件按照每天、每周、每月或每年的规则寻找未来仍可发生的计划时间。
- 每月或每年计划遇到本周期不存在的日期时，直接跳过该周期，不顺延也不改成月末。例如每月 29 日提醒在平年 2 月不发生，1 月 29 日之后的下一次为 3 月 29 日；每年 2 月 29 日提醒在非闰年不发生。
- 一次性事件的时间已经过去时，提示一次“已跳过”，不安排下一次，事件自动关闭。

### 4.2 暂停、离线、睡眠、息屏和锁屏

- 指定时间事件只在计划规定的时间产生提醒，不把暂停时间或软件离线时间从日历计划中扣除。
- 指定时间落在单项暂停、全部暂停或软件未运行期间时，记为“已跳过”，满足真正恢复条件后提示。
- 指定时间落在实际睡眠或休眠期间时，不发送普通提醒；唤醒并满足真正恢复条件后提示“已跳过”。
- 息屏或锁屏时可以选择：
  - 到点后发送普通提醒；
  - 到点时不提醒，恢复后提示一次“已跳过”。
- 循环事件提示“已跳过”后，继续寻找第一个未来计划时间；一次性或已经没有未来计划的事件则关闭。

### 4.3 不保存“单次计划已处理”字段

- 程序不为了防止同一个过去事件反复提示，而给每次计划额外保存“是否已经处理”的字段。
- 对一次性或已经没有未来计划的事件，是否需要处理由当前时间、计划内容和事件开关判断：事件处于开启且计划已过时提示一次“已跳过”，随后关闭；以后因为开关已经关闭，不会再次提示。
- 对循环事件，程序依据不可提醒区间和循环规则判断期间是否发生过计划，并在处理后直接计算第一个未来计划时间；不在通知中展示该时间。

## 5. “已跳过”汇总通知

### 5.1 产生条件

以下情况会产生等待恢复提示的“已跳过”结果：

- 指定时间事件在软件未运行期间到点；
- 指定时间事件在单项暂停或全部暂停期间到点；
- 事件在实际睡眠或休眠期间到点；
- 息屏或锁屏策略选择“不提醒”，且期间到点；
- 固定间隔事件采用继续计时，但设置为在息屏或锁屏期间不发送普通提醒，且期间到点；
- 主动退出软件时，仍有已经显示、带“完成”“延迟”“跳过本次”按钮但尚未由用户处理的普通通知。

### 5.2 汇总规则

- 同一个事件在同一段不可提醒状态中错过一次或多次，都只在汇总中出现一次。
- 不计算或显示具体错过次数。
- 不同事件的错过结果合并成一条“已跳过”通知，并列出事件名称。
- “已跳过”通知是纯信息通知，不提供完成、延迟或跳过按钮。
- 通知中不显示各事件的下一次提醒时间。
- 循环事件仍在程序内部计算下一次时间，以便继续调度。
- 发送汇总通知时，对汇总中列出的每个不同事件分别扣减 1 次终止次数。
- 同一个事件在同一段不可提醒状态中即使错过多次，也因为只汇总一次而只扣减 1 次。
- 多个普通事件恰好在同一计划时间到点时不合并；每个事件分别发送一条带操作按钮的普通通知。

## 6. 通知未处理时的结果

- 用户点击通知右上角的 Windows 关闭叉号：按“跳过本次”处理。
- 通知在用户没有操作的情况下自行消失：按“延迟”处理，并通过统一延迟解析规则设置当前剩余时间。
- 两种关闭原因的业务结果不同，程序必须能够区分：点击叉号走跳过逻辑，自动消失走延迟逻辑。
- 点击叉号后，跳过本次并从本次通知发出的时刻计算下一轮；自动消失后不进入下一轮，而是在延迟倒计时结束后再次发送同一次提醒。
- 自动消失只结束屏幕上的通知横幅；未处理通知仍保留在 Windows 通知中心并保持操作有效。用户在延迟倒计时结束前处理该通知时，以用户后续选择的完成、延迟、跳过或关闭结果更新事件。
- 点击通知中心内保留通知的正文时，重新弹出同一提醒横幅并再次显示三个操作按钮；正文点击本身不改变提醒业务状态，也不打开主面板。
- 通知自动消失时间使用设置页面中的全局统一下拉选项，不再按事件分别保存；下拉框只列出 Windows 通知机制实际支持的自动消失时长，不接收任意数字。
- 自动消失时间只决定通知横幅保留多久；通知自行消失或用户明确点击“延迟”按钮时，均使用同一套默认 5 分钟、可在设置中统一修改且受超间隔策略控制的延迟规则。
- 用户通过通知按钮处理事件时，只执行该操作，不自动显示主面板。
- 普通提醒已经发出但尚未处理时，如果随后发生锁屏或者实际睡眠、休眠，则立即把该通知按“延迟”处理，不再继续等待原通知操作；事件使用与主动延迟相同的本次延迟时长重新计时。
- 用户主动退出程序时仍未处理的普通通知，不再等待原通知操作；下次真正恢复时纳入“已跳过”汇总。

## 7. 保存、退出和异常中断

### 7.1 主动退出

- 完整退出只能通过托盘图标右键菜单中的“退出”。
- 主动退出前保存所有恢复所需的事件配置、开关、暂停属性、当前剩余时间、限时全部暂停剩余时间和待恢复结果。
- 下次启动后，先读取已经保存的事件与状态，再启动调度，避免先创建一套新计时后再覆盖。
- 状态、备份和原子写入临时文件分别位于软件实际目录下的 `Data\state.dat`、`Data\state.bak` 和 `Data\state.tmp`。
- 状态路径以可执行程序实际所在目录为基准，不使用进程当前工作目录，也不改存到 `%AppData%` 或 `%LocalAppData%`。

### 7.2 配置即时保存与运行期间低频保存

- 正常运行期间约每 1 小时保存一次状态。
- 1 小时是低频保存方向，不要求计时非常精确；重点是减少频繁磁盘写入和资源使用。
- 新建事件、删除事件，以及成功修改事件名称、事件类型、时间计划、终止次数、开关或息屏/锁屏策略后，立即请求一次后台保存。
- 执行全部暂停、全部恢复或全部重启后，也立即请求一次后台保存。
- 全部暂停期间设置或更改限时暂停倒计时后，立即保存所选时长、当时的暂停剩余时间和事件冻结状态。
- 多个紧邻的即时保存请求允许合并为一次写入，但必须以最后一次操作后的完整状态为准；保存不得阻塞界面线程。
- 设置完成后限时暂停倒计时的继续流逝，以及单项暂停、单项恢复、单项重启、完成、延迟、跳过和其他单纯倒计时流逝，仍不要求每次立即写入磁盘，由约一小时低频保存和最终退出保存承担。
- 如果程序被强制结束，限时暂停允许恢复到最近一次即时保存或低频保存中的剩余时间，不追求保存强制退出瞬间的精确值。
- Windows 正常关机仍按最终保存原则处理，不为倒计时变化引入持续写盘。

### 7.3 异常退出的可接受回退

- 程序异常退出、被强制结束或系统未给予正常保存机会时，可以恢复到最近一次即时保存或低频保存结果。
- 因此产生的小幅剩余时间或提醒节奏回退是已接受的结果。
- 本项目不为了极少发生的异常情况增加高频保存和额外资源消耗。
- 正式状态无法解密、完整性检查失败、无法解析、结构版本不受支持或字段校验失败时，不得把该数据交给提醒调度，并自动尝试载入 `Data\state.bak`。
- `state.bak` 也无法恢复时，程序使用独立窗口显示恢复失败；用户确认后关闭提示，并按照无有效存档的流程继续启动。

### 7.4 非法界面输入与保存边界

- 文本框中的编辑中内容属于 UI 临时状态，只有完成整组校验后才允许更新 Logic 中的事件状态。
- 固定间隔拆分输入在按下 Enter 或焦点离开整个表单区域时统一校验；输入框之间切换焦点不提交。
- 固定间隔中的空分量按 0 参与整组换算；只有整组总值小于 1 分钟、超过 365 天或包含其他非法内容时才拒绝提交。
- 校验失败时不改变事件的有效配置，不发送持久化变更通知，也不把非法文本写入状态文件。
- 持久化始终从 Logic 导出完整有效状态，不读取 UI 文本框草稿；因此非法文本仍留在界面时，其他设置触发的即时保存或低频检查点仍保存该字段最后一次合法值。

## 8. 精确时间边界

- 计划时间早于真正恢复时刻：属于不可提醒期间发生的计划，按“已跳过”处理。
- 计划时间恰好等于真正恢复时刻：按正常到点提醒处理。
- 计划时间恰好等于暂停开始时刻或软件退出时刻：属于不可提醒期间，恢复后按“已跳过”处理。
- 同一时刻有多个不同事件到点：各事件分别产生普通提醒，不设置跨事件的“同一计划时间只能有一个提醒”限制。
- 同一事件在一段不可提醒时间内发生多次：恢复汇总只列一次，但循环调度仍计算第一个未来计划时间。

## 9. 系统时间和时区变化

- 不为系统时间或时区变化增加专门的历史校正机制。
- 判断时使用当前系统时间、事件计划和事件开关状态。
- 当前时间已经超过尚未处理的计划时间时，按“已跳过”处理；尚未到计划时间时，继续等待正常提醒。
- 一次性事件正常处理或提示“已跳过”后已经关闭。之后即使调整时区让同一钟点再次变为未来，也不会因为该事件已经关闭而再次提醒。
- 时间或时区变化不要求还原绝对历史，只要求现有时间和开关规则能够继续运行，并且不因此导致程序崩溃。

## 10. 终止次数与当前闭环状态

- 事件不再设置截止时间，只使用终止次数控制自动结束。
- 终止次数下拉菜单为“不终止”或 1 次至 100 次，默认“不终止”。
- 只有用户对普通提醒执行“完成”或“跳过本次”后才扣减 1 次。
- 点击关闭叉号属于“跳过本次”，因此扣减 1 次。
- 通知自行消失属于“延迟”，因此自动消失时不扣减。
- 点击“延迟”不扣减；延迟后再次出现仍属于同一次提醒，最终完成或跳过时总共只扣减 1 次。
- 软件未运行、暂停、睡眠或其他不可提醒状态产生的纯信息“已跳过”汇总也扣减终止次数：汇总中每个不同事件分别扣减 1 次，同一事件在同一段不可提醒状态中错过多次仍只扣减 1 次。
- 有限次数减到 0 后，事件自动关闭。
- 因为下拉菜单没有“0 次”，自动关闭后显示“不终止”。事件已经关闭，因此不会继续触发；以后如果用户主动重新开启，则使用界面当前显示的“不终止”设置。
- 指定时间事件选择“仅一次”时，不显示终止次数设置；该事件按照一次性计划自身的完成或错过规则关闭。
- 息屏和锁屏正式共用一套策略，不再分别保存。

此前已经闭环的暂停恢复、重启基点、延迟默认时长、月末和闰日计划仍然有效；通知自行消失以本节最新规则为准。
