- 规划日期：2026-07-24
- 当前基线：`0.1.1`
- 计划状态：用户已确认下一阶段功能范围，尚未开始实施
- 当前阶段：准备完整事件时间模型，并在下一次实现中同步完成动画刷新率自适应

本文档记录下一阶段已经确认的功能范围，以及实现这些功能时采用的阶段拆分和技术建议。用户已确认第 2 节列出的功能范围；更细的类名、内部结构和列表虚拟化方案仍可依据验证结果调整。

## 1. 已确认的实施边界

- 初步简易版本已经基本成型，下一阶段继续完善事件相关功能。
- 暂不实现完整退出、数据保存、启动恢复和异常退出恢复。
- 等事件功能和事件模型基本完整后，再依据最终字段统一设计持久化数据格式。
- 删除事件后，下方卡片应平滑上移填补空位。
- 版本号移动到主页左上角，放在程序图标旁或程序名称旁。
- 所有界面动画同时追求流畅和低资源占用。
- 动画不固定为 60 帧或预先生成固定数量的中间画面；使用持续时间和实际经过时间推进，在系统允许时跟随 WPF 与 DWM 的实际渲染节奏。
- 多显示器刷新率不一致或窗口跨显示器移动时，不手工假设主显示器刷新率，动画总时长和速度保持一致。

## 2. 已确认的下一里程碑

下一里程碑聚焦“完整事件时间模型”，把当前只有固定间隔的基础闭环扩展为两类事件都能真实运行的闭环，不加入存储、退出和系统状态处理。

已确认范围：

1. 建立固定时间事件与指定时间事件共用的可扩展事件结构。
2. 实现事件类型切换和两类事件的条件化表单。
3. 实现指定时间事件的仅一次、每天、每周、每月和每年计划。
4. 实现固定时间事件及可循环指定时间事件的终止次数。
5. 让两类事件共用最近到期调度、通知操作和倒计时。
6. 完成新增日期、时间和次数字段的输入校验。
7. 回归跨日、跨月、闰年、缺失日期和过去时间等边界。
8. 移除现有删除动画的固定 60 帧上限，并回归滚动、定位、删除等动画在不同渲染频率下的时间一致性。

删除事件后的卡片重排动画和左上角版本号在进入该里程碑前单独完成，不占用下一阶段的事件功能范围。下一里程碑完成后，单条事件的“时间怎么设、何时提醒、提醒后是否继续”形成完整闭环；息屏、锁屏、睡眠、错过汇总和限时全部暂停留到后续阶段。

## 3. 删除重排动画的低占用方案

### 3.1 推荐算法

采用记录前后位置差值的 FLIP 思路：

1. 用户确认删除后，记录当前可见事件卡片的纵向位置。
2. 让被删除卡片进行一次很短的淡出反馈。
3. 从事件集合删除目标，只允许列表完成一次正常布局。
4. 记录仍然可见的受影响卡片的新位置。
5. 对每张受影响卡片设置 `TranslateTransform.Y = 旧位置 - 新位置`。
6. 只把 `TranslateTransform.Y` 从该差值动画到 `0`，视觉上表现为下面的卡片平滑顶替上来。
7. 动画结束或被新操作打断后，立即清除动画、变换和完成回调。

### 3.2 资源控制

- 不逐帧修改 `Height`、`Margin`、行高或其他会触发布局的属性。
- 动画只作用于当前已经生成且用户能看到的受影响卡片；屏幕外卡片不参加动画。
- 使用短时、非循环动画，建议总时长约 `160–220 ms`，采用自然减速，不使用弹跳。
- 窗口不可见、Windows 关闭界面动画或没有可见受影响卡片时，直接删除，不启动动画。
- 动画完成后不保留 `CompositionTarget.Rendering` 订阅、`DispatcherTimer` 或活动动画时钟。
- 连续操作时取消旧动画并从当前视觉位置重新计算，避免累积变换或卡片错位。
- 不调用 `Timeline.SetDesiredFrameRate` 将普通交互动画限制为 60 帧；WPF 时间线动画继续以毫秒持续时间定义。
- 使用 `CompositionTarget.Rendering` 的自定义动画必须依据实际经过时间计算进度，不能假设每次回调固定经过 `1/60` 秒。
- 不为普通 WPF 交互增加显示器刷新率轮询。窗口跨显示器时由 WPF 与 DWM 提供实际渲染时机，应用只保证时间计算与回调频率解耦。

### 3.3 长列表优化

建议在实现完整事件表单前评估把当前普通 `ItemsControl` 列表换成支持 UI 虚拟化和容器回收的列表容器：

- 只为可见事件创建较重的双行卡片视觉树。
- 使用 `VirtualizingStackPanel` 和 `VirtualizationMode=Recycling` 回收离屏容器。
- 所有事件状态仍存放在 ViewModel 或 Logic 中，不存放在可能被回收的卡片容器上。
- 平滑滚动、新增定位和删除重排只操作已经实现的可见容器。

如果虚拟化迁移影响现有像素级平滑滚动，应先制作小型验证并比较资源与交互结果，再决定是否在本里程碑一并替换列表容器。

## 4. 事件模型建议

### 4.1 共同部分

每条事件继续共用：

- `event id`；
- 名称；
- 开启和暂停状态；
- 当前倒计时或下一计划时间；
- 当前通知身份与提醒处理状态；
- 终止策略；
- 后续系统状态策略接口。

### 4.2 时间计划部分

时间计划独立成可替换的计划结构：

- 固定间隔计划：间隔、当前剩余时间和下一到期时间；
- 指定时间计划：频率、日期或星期字段、时分字段和下一有效计划。

下一次提醒时间由独立的纯计算组件生成，调度器只接收“当前最近到期时间”，不在计时器内部混入每月、每年等日历判断。这样后续增加事件类型或新的循环频率时，不需要重写通知和 UI 刷新流程。

### 4.3 终止次数

- “不终止”与 `1–100` 次使用共同模型。
- 只有完成、跳过或纯信息“已跳过”汇总才扣减。
- 延迟和自动消失不扣减。
- 指定时间“仅一次”隐藏终止次数并按一次性规则自动关闭。

## 5. 建议实施顺序

### 阶段 A：交互和动画基础

- 实现删除重排动画。
- 移动版本号。
- 建立统一、可中断、可清理的轻量动画辅助组件。
- 移除统一动画辅助组件中的固定 60 帧上限，保持滚动等自定义动画按实际经过时间推进。
- 验证窗口隐藏和关闭系统动画时不会运行无意义动画。

### 阶段 B：事件时间模型

- 将当前固定间隔字段整理为明确的计划结构。
- 增加指定时间频率与计划字段。
- 增加共享终止策略。
- 保持现有固定间隔行为和通知状态机不回退。

### 阶段 C：条件化事件表单

- 实现事件类型滑块。
- 实现固定间隔、指定时间和频率对应的动态输入字段。
- 指定时间事件将“重启”置灰。
- 实现所有新增字段的合法性校验和错误提示。

### 阶段 D：调度与通知闭环

- 计算一次性、每天、每周、每月和每年的下一有效计划。
- 月度或年度不存在目标日期时跳过当前周期。
- 两类事件继续共用一个最近到期计时器。
- 完成、延迟、跳过、叉号关闭和自动消失按既有规则更新事件。
- 扣减终止次数并在归零后关闭事件。

### 阶段 E：回归与验收

- 固定间隔原有功能全部回归。
- 对频率、跨日、跨月、闰年、缺失日期和过去时间进行逻辑测试。
- 检查新增表单在 `760 × 560` 最小窗口和常用宽屏窗口下的排版与横向滚动。
- 检查添加、删除、滚动和高亮动画能被打断且不会残留变换。
- 检查代码不再对普通界面动画设置固定 60 帧上限；在可用硬件上分别观察 60 Hz、100 Hz 以上以及不同刷新率多显示器之间移动窗口时的动画，确认总时长和速度没有明显变化。
- 测量动画期间 CPU 峰值和动画结束后的空闲 CPU，确认不存在持续动画工作。
- Debug 和 Release 构建保持零警告，界面无乱码。

## 6. 本里程碑明确不做

- 息屏和锁屏策略的真实检测与处理。
- 睡眠或休眠后的“已跳过”汇总。
- 限时全部暂停。
- 事件搜索。
- 设置页面、全局通知时长与延迟时长编辑。
- 开机启动、静默启动、版本检查和自动更新。
- 主题切换。
- 完整退出。
- 数据保存、启动恢复和异常退出恢复。

## 8. 规划依据

- WPF 官方建议动画优先使用 `RenderTransform`，因为它在布局完成后改变呈现，通常比 `LayoutTransform` 更有性能优势：
  <https://learn.microsoft.com/en-us/dotnet/desktop/wpf/graphics-multimedia/transforms-overview>
- WPF 官方性能说明指出，布局遍历会随子元素数量增加而增加；更新现有 `RenderTransform` 可以避免不必要的布局计算：
  <https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/optimizing-performance-layout-and-design>
- WPF 官方建议长列表使用 UI 虚拟化和容器回收，只为可见项目创建视觉容器：
  <https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/optimizing-performance-controls>
- WPF 动画由时间线和时钟按当前时间计算进度，实际计时器 tick 数量会随系统资源而变化，因此普通动画应以持续时间而不是固定帧数定义：
  <https://learn.microsoft.com/en-us/dotnet/desktop/wpf/graphics-multimedia/animation-and-timing-system-overview>
- `CompositionTarget.Rendering` 在每个实际渲染帧前触发，并提供当前呈现时间；需要自定义逐帧处理时，应使用真实经过时间更新状态：
  <https://learn.microsoft.com/en-us/dotnet/desktop/wpf/graphics-multimedia/property-animation-techniques-overview>
