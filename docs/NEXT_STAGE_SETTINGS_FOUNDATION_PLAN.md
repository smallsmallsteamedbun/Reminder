# Reminder 下一阶段：通知延迟设置与事件搜索计划

- 规划日期：2026-07-28
- 基线版本：`0.5.0`
- 计划状态：建议草案，等待用户确认
- 实施授权：尚未授权；确认计划且完成备份后再修改代码
- 关联需求：`docs/REQUIREMENTS.md`
- 现有设置页：`docs/SETTINGS_PAGE_DESIGN.md`

## 1. 阶段判断

`0.5.0` 已经完成主页、事件页、设置页外壳以及渲染模式设置。用户本轮已经补齐通知延迟动态表单和事件名称搜索的主要规则，因此建议把下一阶段收敛为“通知延迟设置、事件搜索、设置页排版和既有功能回归”。

这比同时加入主题、开机自动启动和静默启动更适合作为紧邻 `0.5.0` 的小阶段：

- 事件搜索范围小、依赖少，能够直接改善事件较多时的使用效率；
- 通知延迟已经有实际业务逻辑，先把现有固定值变成可配置项，可以验证设置、持久化和提醒逻辑之间的完整链路；
- 主题会影响几乎全部视觉资源，开机启动和静默启动会扩展 Windows 启动生命周期，适合放在后续独立阶段，避免本阶段同时改变过多系统边界；
- 自动更新继续暂缓，等待用户确定 GitHub 或服务器上的版本与安装包来源。

## 2. 建议实施范围

### 2.1 设置模型与状态迁移

- 在现有应用设置中增加“统一通知延迟总分钟数”和“事件提醒间隔短于统一延迟时的处理策略”两个类型化字段。
- 延迟时长内部只保存合法的总分钟数，不保存当前展开了几个输入框。
- 处理策略使用稳定枚举或等价类型，不把下拉框显示文字直接写入持久化状态。
- 状态文档升级到下一结构版本；旧状态的通知延迟迁移为 5 分钟。
- 策略默认值尚未由用户确认，确认前不实施迁移默认值。
- 设置变化继续使用现有串行即时保存，不建立第二套设置文件或保存队列；非法界面草稿不得覆盖上一份合法设置。

### 2.2 可复用的动态时长输入

- 把固定时间事件已有的“分钟—小时—天”换算、校验和提交规则整理成小型可复用组件或共享逻辑，通知延迟表单复用同一规则。
- 默认 5 分钟时只显示“分钟”输入框；达到 60 分钟后显示“小时、分钟”，达到 24 小时后显示“天、小时、分钟”。
- 最大值为 365 天，不显示“年”。
- 按 Enter 或焦点离开整个表单区域时统一确认；空分量按 0 处理，合计为 0、超过上限、非数字或溢出输入不应用。
- 复用只覆盖时长输入和校验，不把固定事件的调度状态或通知设置业务塞进视觉控件。

### 2.3 通知延迟设置与提醒逻辑

- 在设置页的通知区域加入“统一通知延迟时间”动态时长表单。
- 加入“事件提醒间隔短于统一延迟时”的策略下拉框；最终显示文案、默认项和适用事件类型在用户确认后实施。
- 通知中的“延迟”按钮与通知自动消失都通过同一个延迟时长解析入口取得本次延迟，不在两个回调中重复判断。
- 继续沿用“直接修改当前剩余时间、不建立独立延迟状态、延迟不扣终止次数”的既有规则。
- 成功修改设置后立即请求后台保存；无效输入只停留在界面草稿中，后续其他即时保存和一小时低频保存仍使用上一份合法值。

### 2.4 事件搜索

- 在事件页顶部操作区加入事件名称搜索框。
- 搜索框非空时，只显示名称包含搜索字段的事件。
- 搜索文本包含空格时，把空格分隔的字段按“并且”关系匹配。
- 搜索框非空时在末尾显示清空叉号，点击后清空搜索并恢复完整列表。
- 搜索结果只是事件集合的界面投影，不复制事件对象，不改变原事件顺序、调度状态或持久化内容。
- 搜索期间新增事件、修改名称和执行全部操作的具体交互，在用户确认后实施。

### 2.5 设置页布局

- “完善设置页布局”是把渲染模式和新增通知设置按照统一的分组、标签、说明、输入框、下拉框、间距与错误状态排好。
- 该工作不代表额外增加未确认的设置功能，也不把尚未实施的条目做成无效占位开关。
- 默认窗口和允许的最小窗口下都应能阅读和操作；内容超出可用高度时使用与现有风格一致的滚动方式。

## 3. 建议实施顺序

### 阶段 A：确认剩余产品边界

- 确认策略下拉框的最终文字、默认项和适用事件类型。
- 确认搜索的大小写、连续空格、无结果、新增与改名交互，以及全部操作是否越过筛选结果作用于全部事件。
- 通知自动消失时间的输入方式若仍未确认，则不阻塞本阶段其他内容。

### 阶段 B：动态时长输入与设置迁移

- 整理可复用的时长换算和校验边界。
- 扩展类型化设置、持久化映射、旧状态迁移和即时保存。
- 先用逻辑测试覆盖 59/60 分钟、23/24 小时、365 天、空分量、自动进位、非法输入和溢出输入。

### 阶段 C：通知延迟逻辑

- 建立单一的“解析本次延迟时长”逻辑入口。
- 接入通知延迟按钮、通知自动消失、锁屏或睡眠时对未处理通知执行的延迟处理。
- 验证延迟后仍是同一次提醒、终止次数不扣减、重启后恢复正确剩余时间。

### 阶段 D：设置页与事件搜索

- 完成通知设置分组、动态时长表单、策略下拉框和错误状态。
- 完成事件页搜索框、多字段并且匹配和清空按钮。
- 保持现有事件卡片复用，不为搜索结果创建第二套卡片和业务状态。

### 阶段 E：整体回归与资源复核

- “回归托盘、调度、持久化和两种渲染模式”是重新测试这些既有功能没有被新增设置与搜索带坏，不是重新开发一套托盘、调度或存储。
- 回归托盘打开主页、全部暂停、全部恢复、版本显示、退出保存和窗口隐藏后台运行。
- 回归固定与指定时间调度、通知按钮、自动消失、锁屏或睡眠处理、全部操作和最近到期计时器。
- 回归新设置即时保存、一小时低频保存、退出保存、启动恢复、`state.dat`/`state.bak` 回退及旧状态迁移。
- 分别在“硬件优先渲染”和“软件渲染（兼容模式）”下检查设置页、搜索、事件滚动、页面切换、CPU 和内存。

## 4. 本阶段暂不实现

- 全局通知自动消失时间的设置表单；其输入控件、合法范围和越界处理尚未确认；
- 主题、开机自动启动和静默启动；需求继续保留，建议放入后续独立阶段；
- 版本检查、`new` 标记、自动下载和覆盖更新；
- Inno Setup 安装、卸载及卸载时保留或删除 `Data`；
- 新提醒类型、循环频率、通知操作或统计页面；
- 改变当前硬件优先默认渲染策略。

## 5. 验收标准

- 旧版状态能够迁移，通知延迟和策略设置能够即时保存并在重启后恢复。
- 动态时长输入在分钟、小时、天三个形态间正确转换，非法草稿不会改变 Logic 或磁盘中的上一份合法值。
- 延迟按钮、通知自动消失及其他既有延迟入口都使用相同策略，且延迟仍不扣减终止次数。
- 单字段和带空格多字段搜索结果正确，清空按钮恢复完整事件列表。
- 搜索不会复制或改变事件身份、顺序、调度、开关、暂停和持久化数据。
- 设置页在默认窗口和最小窗口下没有乱码、截断、明显错位或无法操作的控件。
- 两种渲染模式下，托盘、调度、持久化、通知、全部操作和页面导航回归通过，且没有新增持续轮询或空闲动画。
- Debug、Release、设置迁移、通知延迟逻辑、搜索逻辑、界面和既有核心回归全部通过。

## 6. 需要用户确认的计划边界

- 策略下拉框建议使用更完整的动词文案：“缩短为事件提醒间隔”和“仍使用统一延迟时间”；是否采用这组文字。
- 两个策略中哪一个作为默认值。为了延续当前行为并避免延迟时间长于提醒间隔，计划建议默认“缩短为事件提醒间隔”，但尚未视为已确认需求。
- “事件提醒间隔短于统一延迟”的策略是否只适用于固定时间间隔事件；指定时间循环事件是否始终使用统一延迟时间。
- 搜索是否忽略英文大小写、首尾空格和连续空格；计划建议忽略这些差异。
- 搜索生效时点击“添加事件”，是否先自动清空搜索再新增和定位；计划建议先清空，避免默认名称不匹配后新卡片立即消失。
- 修改事件名称后不再匹配搜索条件时，是输入过程中即时消失，还是按 Enter 或离开名称框成功应用后再消失；计划建议成功应用后再更新筛选。
- 全部暂停、全部恢复和全部重启是否始终作用于所有符合条件的事件，而不是只作用于当前搜索结果；计划建议保持全局语义不变。
