# Reminder `0.0.0` 首轮验证记录

- 验证日期：2026-07-23
- 验证对象：`src/Reminder.App`
- 版本：`0.0.0`
- 结论：初步简易版本的核心闭环已经实现并通过首轮验证

本文档作为 `0.0.0` 的历史验证记录集中保存在 `docs/versions/`，只记录当时的实现和验证结果，不增加或改变 `docs/REQUIREMENTS.md` 中的正式需求。

## 1. 已实现闭环

当前版本已经实现：

```text
添加固定间隔事件
→ 校验名称与时间间隔
→ 开始倒计时
→ 单项或全部暂停、恢复、重启
→ 隐藏主窗口后继续后台调度
→ 到点发送 Windows 通知
→ 完成、延迟、跳过、关闭叉号或自动消失
→ Logic 更新事件并安排下一轮
```

两条默认示例事件“喝水”和“休息眼睛”存在、默认关闭且可以删除。新增事件默认开启、未暂停、采用 45 分钟固定间隔。

## 2. 架构检查

首轮代码继续放在同一个 WPF 项目中，并按职责分为：

- `UI`：窗口、样式、绑定和用户操作入口；
- `Logic`：事件状态、输入校验、业务操作和调度；
- `Windows`：Windows 通知和系统托盘；
- `System`：版本、默认参数和运行时辅助能力。

已经保持以下边界：

- UI 不直接控制后台计时器；
- 调度器不引用 WPF 控件；
- 调度器不依赖具体 Windows 通知 API；
- Windows 通知结果通过抽象接口返回 Logic；
- 后台只有一个等待最近到期事件的一次性计时器；
- 界面逐秒刷新只在窗口可见时运行，隐藏后停止。

## 5. Windows 通知真实验证

当前实现使用 `Microsoft.Toolkit.Uwp.Notifications` 提供的兼容接口创建 Windows 原生通知，并保留 Windows 的原生排列和关闭入口。

已经在真实 Windows 通知中分别验证：

| 操作 | 平台或应用层结果 | 业务结果 | 验证 |
|---|---|---|---|
| 点击“完成” | `Complete` | 从完成时间开始下一轮 | 通过 |
| 点击“延迟” | `Snooze` | 剩余时间改为默认 5 分钟 | 通过 |
| 点击“跳过本次” | `Skip` | 从本次通知时间保持正常顺延 | 通过 |
| 点击关闭叉号 | `UserClosed` | 映射为跳过本次 | 通过 |
| 10 秒没有操作 | `TimedOut` | 映射为默认延迟 | 通过 |

直接使用 Windows `ToastNotification.ExpirationTime` 时，当前系统会把程序性到期报告为与关闭叉号相同的 `UserCanceled`，无法满足区分要求。因此当前实现改为：

1. 通知显示时启动一个对应通知的一次性 10 秒计时器；
2. 用户先点击按钮或关闭叉号时，原子地完成该通知并取消计时器；
3. 计时器先到期时，应用从通知历史移除该通知并只上报一次 `TimedOut`；
4. 并发字典保证竞态下同一通知只处理一次。

真实自动消失验证中，通知约在显示 10 秒后返回 `TimedOut`；真实关闭叉号验证返回 `UserClosed`，两者已经区分。

当前点击通知正文暂时按“跳过本次”处理。这是首轮实现行为，不是新增的正式需求，后续可以单独确定通知正文应当如何响应。

## 6. 界面验证

通过 WPF 离屏渲染分别检查了正常窗口、窄窗口和非法输入状态：

- 正常窗口尺寸：`1180 × 760`；
- 窄窗口尺寸：`760 × 560`；
- 非法输入：空名称和超大时间间隔。

检查结果：

- 中文名称、按钮、状态、倒计时和错误提示未出现乱码；
- 顶部标题、版本、全局按钮和事件卡片未发生遮挡；
- 事件卡片保持双行结构；
- 窄窗口下卡片可以独立横向滚动；
- 非活动事件降低视觉强调但仍可读取；
- 空名称和非法数值显示红色边框与中文就地错误；
- 未实现功能没有以可点击空壳控件出现。

首轮渲染中曾发现根背景透明及主按钮文字颜色继承错误，均已修正后重新检查。

## 7. 后台与资源占用

窗口生命周期测试已经通过：

- 点击窗口关闭按钮后窗口隐藏，进程和调度继续存在；
- 托盘双击或菜单可以重新打开主页；
- 窗口隐藏后 UI 秒级刷新停止；
- 软件渲染诊断环境中，隐藏并整理工作集后测得约 `46.5 MB`；
- 20 秒空闲 CPU 采样为 `0%`。

资源数据存在一个必须保留的限制：

- 当前自动化工具运行在非交互桌面，WPF 硬件渲染在该环境中出现异常高占用，独立的最小 WPF 程序也能复现，因此不能用该数据评价 Reminder；
- 切换为仅供诊断的软件渲染后，Reminder 界面显示状态测得约 `169–205 MB`，高于“尽量低于 160 MB”的目标；
- 正式启动默认仍使用 WPF 硬件渲染，没有为了测试数据强制软件渲染；
- 界面显示时内存目标需要在用户的普通 Windows 桌面中重新测量，当前不能宣称已经满足；
- 隐藏状态低于 100 MB 和空闲 CPU 低于 1% 已在诊断环境中满足。

如需复现软件渲染诊断，可在启动前把环境变量 `REMINDER_SOFTWARE_RENDERING` 设为 `1`；正常使用不需要设置。

## 9. 当前临时边界

为使首轮输入校验可运行，代码暂时采用：

- 事件名称最多 40 个字符；
- 固定间隔为 1 至 525600 分钟；
- 自动消失为 10 秒；
- 默认延迟为 5 分钟。

前两项尚未被确认为长期产品边界，不写入正式需求；后续讨论时可以调整。

## 10. 普通桌面复核步骤

1. 用 Visual Studio 打开 `Reminder.slnx`。
2. 将 `Reminder.App` 设为启动项目并按 `F5`。
3. 检查中文、窗口缩放和系统 DPI 下的排版。
4. 新增一个 1 分钟事件，测试暂停、恢复、重启和隐藏窗口。
5. 分别测试三个通知按钮、关闭叉号和等待 10 秒自动消失。
6. 在任务管理器中记录界面显示、界面隐藏和长时间空闲时的内存、CPU。

普通桌面复核如发现 DPI、字体、通知策略或资源占用差异，应把环境和结果追加到本文档，再进行针对性修正。
