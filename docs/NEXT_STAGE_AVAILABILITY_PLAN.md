# Reminder 下一阶段：不可提醒状态闭环实施规划

- 规划日期：2026-07-24
- 规划状态：待用户确认
- 当前版本：`0.2.0`
- 本文性质：实施建议，不代表已经完成，也不把尚未确认的实现建议写成正式需求

## 1. 规划结论

建议下一个阶段实现到“不可提醒状态形成完整运行闭环”的程度。

这个里程碑不只接入 Windows 的息屏、锁屏和睡眠事件，还应先把单项暂停、全部暂停和系统状态拆成互不覆盖的运行状态，再完成限时全部暂停、错过事件汇总以及单条事件的息屏/锁屏策略。

完成后，软件应具备以下用户可见能力：

1. 单项暂停、全部暂停和系统状态可以同时存在，恢复其中一个状态不会误恢复其他状态；
2. 全部暂停可以选择手动恢复或既定的快捷时长，并显示限时暂停的剩余时间；
3. 每个事件可以按已经确认的表单设置息屏和锁屏策略；
4. 程序可以实际响应锁屏、解锁、息屏、亮屏、睡眠、休眠和唤醒；
5. 不可提醒期间到点的事件按照规则继续、重启、冻结或记为已跳过；
6. 恢复后只发送一条无按钮的“已跳过”汇总，并正确处理终止次数和一次性事件；
7. 主面板隐藏后仍正常工作，不依赖高频轮询。

## 2. 为什么不直接进入存储阶段

完整事件时间模型已经存在，但事件最终需要保存的运行属性还没有稳定：

- 单条事件尚未保存息屏和锁屏策略；
- 当前全部暂停直接修改每个事件的 `IsPaused`，无法区分单项暂停和全局暂停；
- 尚未维护限时全部暂停状态；
- 尚未维护 Windows 锁屏、息屏和睡眠状态；
- 尚未维护等待恢复提示的错过事件集合。

如果现在先设计持久化结构，完成上述功能时仍要增加和迁移多项状态字段。先完成不可提醒状态闭环，再进入 DPAPI 存储和启动恢复，可以减少一次明显的数据结构返工。

## 3. 当前实现基础和真实改动面

### 3.1 可以直接复用

- 固定时间事件和指定时间事件已经共用事件结构、通知响应和最近到期调度器；
- 日历计划已经可以计算一次性、每天、每周、每月和每年的下一次发生时间；
- 通知服务已经具备 `ShowMissedEvents` 入口，可以显示无操作按钮的汇总通知；
- 主面板隐藏后后台调度继续运行；
- `Logic`、`UI`、`Windows`、`System` 的目录和职责边界已经存在；
- 界面已经具有下拉表单、输入验证、动态显示和秒级倒计时的基础组件。

### 3.2 必须先修正

当前 `ReminderEngine.PauseAll()` 会逐个把事件设为 `IsPaused = true`，`ResumeAll()` 又逐个恢复。这种实现无法表达：

- 事件原本已被用户单独暂停，之后又发生全部暂停；
- 全部暂停结束，但单项暂停仍应保留；
- 事件被锁屏策略暂停，同时又处于全部暂停；
- 先息屏、再锁屏、再睡眠，随后以不同顺序恢复。

因此下一阶段不能继续增加更多布尔分支到现有暂停方法中，而要先建立分层的有效运行状态。

## 4. 建议实施范围

### 4.1 分层运行状态

在逻辑层分别维护：

- 单项暂停：只属于固定时间事件，由事件的暂停/恢复按钮控制；
- 全部暂停：属于整个程序，包含手动恢复或限时恢复；
- Windows 状态：至少包含锁屏、息屏和睡眠三个独立事实；
- 事件策略：决定固定时间或指定时间事件在息屏和锁屏期间如何处理；
- 等待恢复的已跳过事件：按事件 ID 去重。

逻辑层根据这些状态统一计算“当前是否可以正常提醒”，而不是让 UI 或 Windows 回调直接修改事件计时。

状态发生重叠时，只有全部阻止条件都解除才算恢复。例如先息屏后锁屏，即使亮屏，只要仍未解锁，就不能发送恢复汇总。

### 4.2 全部暂停闭环

实现已经确认的选项：

- 直到手动恢复；
- 5 分钟；
- 10 分钟；
- 15 分钟；
- 30 分钟；
- 1 小时；
- 2 小时；
- 5 小时。

具体行为：

- 点击全部暂停后显示时长下拉表单；
- 默认选择“直到手动恢复”；
- 限时暂停时显示剩余时间，手动恢复时不显示；
- 固定时间事件冻结当前剩余时间，恢复后继续；
- 指定时间事件在暂停期间发生计划时记入“已跳过”；
- 全部恢复只解除全局暂停，不改变原有单项暂停；
- 全部重启仍只影响满足条件的固定时间事件。

后台只需要维护一个全局暂停到期时刻。调度时可以把该时刻和各事件到期时刻共同交给最近到期调度机制，不增加持续轮询；界面可见时再使用现有轻量刷新机制显示秒级剩余时间。

### 4.3 单条事件的息屏和锁屏表单

固定时间事件显示：

- 继续计时；
- 重新计时；
- 暂停计时。

选择“继续计时”后，再显示：

- 提醒；
- 不提醒。

默认值为“暂停计时”；继续计时的附加选项默认“不提醒”。

指定时间事件显示：

- 提醒；
- 不提醒。

默认值为“不提醒”。

这些属性属于事件设置。修改成功后继续采用已经确认的联动规则：事件自动开启并解除单项暂停。

### 4.4 Windows 状态监测

在 `Windows` 模块建立一个只报告系统事实的状态监测器：

- 锁屏和解锁：监听 Windows 会话切换事件；
- 息屏和亮屏：桌面进程注册会话显示状态通知；
- 睡眠、休眠和唤醒：监听系统电源模式变化；
- 监测器只输出状态快照或状态变化事件，不决定提醒如何计时。

建议使用独立、不可见的 Windows 消息接收窗口或等价的 `HwndSource`，避免把电源消息处理写入主界面代码。主面板隐藏时，消息接收和后台逻辑仍继续工作。

所有静态系统事件、窗口消息钩子和原生注册句柄都必须在释放时取消订阅或注销，避免长期运行后产生泄漏。

### 4.5 各事件类型的系统状态行为

#### 固定时间事件

- 继续计时并提醒：保持原节奏，到点发送普通通知；
- 继续计时但不提醒：保持原节奏，期间到点时按事件 ID 记入一次“已跳过”，恢复后继续下一个未来节奏；
- 重新计时：系统状态结束后，从一个完整间隔重新开始；
- 暂停计时：进入对应状态时冻结当前剩余时间，恢复后继续。

#### 指定时间事件

- 提醒：计划到点时发送普通通知；
- 不提醒：期间发生计划时记入一次“已跳过”，恢复后继续寻找下一个未来计划；
- 一次性事件错过后在汇总处理时关闭；
- 循环事件继续保持原有日历规则。

#### 实际睡眠或休眠

- 不提供用户策略；
- 睡眠或休眠期间不发送普通提醒；
- 唤醒后检查期间是否到点；
- 同一事件无论发生几次，只记入一次“已跳过”；
- 固定时间事件保持原有时间节奏，循环指定时间事件继续计算下一次未来计划。

### 4.6 “已跳过”汇总

逻辑层维护按事件 ID 去重的等待集合：

- 同一事件在同一段不可提醒状态中出现多次，只保留一次；
- 不同事件在真正恢复时合并为一条通知；
- 通知只列事件名称，不显示错过次数和下一次时间，也不提供按钮；
- 汇总实际发送时，对其中每个不同事件扣减一次终止次数；
- 终止次数减到零的事件自动关闭；
- 一次性事件在汇总后关闭；
- 如果仍有锁屏、单项暂停或全部暂停等阻止条件，该事件继续留在等待集合中。

为了避免系统时间和真实睡眠让自动化测试不稳定，建议把当前直接读取 `DateTimeOffset.Now` 的位置逐步收口到可替换的时间来源。生产环境仍使用系统时间，测试环境使用可控时间，不改变用户可见行为。

## 5. 建议的内部实施顺序

### 阶段 A：先保持现有行为完成状态拆分

1. 把单项暂停和全部暂停拆开；
2. 建立统一的有效运行状态判断；
3. 保证现有固定间隔、指定时间、通知按钮和倒计时回归不变；
4. 为时间相关逻辑加入可控时间来源。

这一步完成后，即使暂时没有接入 Windows 状态，现有功能也不应退化。

### 阶段 B：完成限时全部暂停和错过集合

1. 实现全部暂停时长和剩余时间；
2. 实现指定时间事件在全部暂停期间的错过判断；
3. 实现无按钮汇总、去重、终止次数扣减和一次性关闭；
4. 验证单项暂停与全部暂停的重叠。

### 阶段 C：加入事件策略和 Windows 监测

1. 扩展事件模型与快照；
2. 加入第二行息屏/锁屏表单；
3. 接入锁屏、显示状态和睡眠事件；
4. 把系统事实交给逻辑层执行事件策略；
5. 处理息屏、锁屏、睡眠相互重叠和不同顺序恢复。

### 阶段 D：集成验证

1. 使用假的系统状态监测器自动测试全部状态组合；
2. 在真实 Windows 桌面手动验证锁屏、解锁、息屏、亮屏、睡眠和唤醒；
3. 验证主面板隐藏后仍能收到状态；
4. 检查没有常驻轮询、遗留计时器或事件订阅；
5. 完成 Debug、Release、界面和资源占用回归。

## 6. 验收标准

至少覆盖以下场景：

1. 单项暂停后再全部暂停，全部恢复后仍保持单项暂停；
2. 限时全部暂停结束后，固定时间事件从原剩余时间继续；
3. 指定时间事件在全部暂停期间到点，恢复时进入汇总；
4. 固定时间事件的继续、重新、暂停三种策略都与文档一致；
5. 指定时间事件的提醒和不提醒两种策略都与文档一致；
6. 睡眠期间所有事件都不发送普通提醒，唤醒后正确汇总；
7. 同一事件错过多次只显示和扣减一次；
8. 多个事件错过时只发送一条汇总，普通同时到点通知仍分别发送；
9. 一次性事件错过后关闭，循环事件继续计算未来计划；
10. 终止次数在汇总时正确扣减，减到零后关闭；
11. 先息屏再锁屏、先锁屏再睡眠等重叠顺序不会提前恢复；
12. 精确等于恢复时刻的计划按正常到点处理，早于恢复时刻才算错过；
13. 主面板隐藏时停止 UI 秒级刷新，但系统监测和后台调度继续；
14. 空闲时不增加高频轮询，CPU 和内存仍以现有目标为准；
15. Debug 和 Release 构建零警告、零错误，界面无乱码和明显错位。

## 7. 现实度评估

| 部分 | 现实度 | 主要原因或风险 |
| --- | --- | --- |
| 分层暂停与有效状态 | 高 | 纯逻辑改造，现有事件模型可继续使用；需要充分回归现有行为 |
| 限时全部暂停 | 高 | 单一到期时刻即可实现，无需频繁轮询 |
| 错过事件汇总 | 高 | 现有通知服务已有无按钮汇总入口，主要工作在状态去重和扣减规则 |
| 锁屏和解锁 | 高 | Windows 提供明确的会话锁定与解锁事件 |
| 睡眠和唤醒 | 高 | Windows 提供挂起与恢复事件；真实机器仍需手动验证 |
| 息屏和亮屏 | 中高 | Windows 提供会话显示状态通知，但需要少量 Win32 互操作，并应在不同显示设备上验证 |
| 锁屏期间普通通知的实际可见形式 | 中 | 应用可以请求发送通知，但最终是否在锁屏界面展示取决于 Windows 和用户通知设置 |
| 全自动真实系统状态测试 | 中 | 逻辑可用假的状态源完整测试，真实锁屏、息屏和睡眠仍需要人工或专门环境验证 |

整体上不存在技术不可行项，也不需要引入新的大型运行环境。最需要控制的是状态组合复杂度，而不是资源占用。

## 8. 本阶段明确不做

- 数据保存、DPAPI、启动恢复、异常恢复和完整退出；
- 事件搜索；
- 独立设置页面，以及全局通知自动消失时长和延迟时长的编辑；
- 主题切换；
- 开机启动和静默启动；
- 版本检查、自动更新和 MSIX 发布；
- 为睡眠或休眠增加用户可选策略；
- 强制点亮显示器或绕过 Windows 的锁屏通知设置。

## 9. 已确认的两个交互

1. 托盘中的“快捷全部暂停”始终采用“直到手动恢复”；
2. 普通提醒已经发出但用户尚未处理时，如果随后发生锁屏或者实际睡眠、休眠，则把该通知按“延迟”处理。

## 10. 官方接口可行性依据

- `SystemEvents.SessionSwitch` 可以报告会话切换，`SessionSwitchReason` 包含 `SessionLock` 和 `SessionUnlock`：
  <https://learn.microsoft.com/en-us/dotnet/api/microsoft.win32.systemevents.sessionswitch?view=windowsdesktop-10.0>
- `SystemEvents.PowerModeChanged` 用于系统挂起和恢复；官方同时提醒静态事件必须在释放时解除订阅：
  <https://learn.microsoft.com/en-us/dotnet/api/microsoft.win32.systemevents.powermodechanged?view=windowsdesktop-10.0>
- 桌面应用可以通过 `RegisterPowerSettingNotification` 注册电源状态通知，并通过 `WM_POWERBROADCAST` 接收变化：
  <https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registerpowersettingnotification>
- 对交互式用户模式应用，Windows 提供 `GUID_SESSION_DISPLAY_STATUS` 报告当前会话的显示器开、关和变暗状态：
  <https://learn.microsoft.com/en-us/windows/win32/power/power-setting-guids>
- WPF 的 `HwndSource.AddHook` 可以处理没有直接 WPF 事件对应的窗口消息：
  <https://learn.microsoft.com/en-us/dotnet/api/system.windows.interop.hwndsource.addhook>
